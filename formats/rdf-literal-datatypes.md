# Literal Datatypes and Language Tags (formats)

## Overview

This exercise finishes the story of the literal that `rdf-triples-basics.md` started. That file established that a literal is a lexical form (a Unicode string) plus a datatype IRI, that a simple literal like `"hello"` is shorthand for the datatype `http://www.w3.org/2001/XMLSchema#string`, and that the quotes are syntax rather than part of the lexical form. Here the question is sharper: when are two literals the *same* RDF term, and when are they merely two terms that happen to mean the same thing? The exercise was a hand-written N-Triples file of seven lines arranged as three pairs plus one ill-typed line, where every pair shares its subject and predicate and differs only in how the literal is written, so that whether a pair collapses into one triple directly reveals whether the two literals are term-equal. A second, deliberately invalid one-line case tested what a parser does with a literal in subject position. This is a `formats` exercise and used rdflib 7.6.0 (through `rdfpipe` and a small helper script) in a disposable `python:3.12-slim` container. It was re-checked live and chosen again because it is still the mainstream, actively maintained Python RDF toolkit, and because its documented `rdflib.NORMALIZE_LITERALS` switch makes it possible to put the spec's behavior and the tool's default behavior side by side. RDF 1.1 Concepts was treated as normative because a live check showed RDF 1.2 Concepts still at Candidate Recommendation.

## Lexical form, value, and term equality

Every datatype has a *lexical space* (the strings it accepts), a *value space* (the things those strings denote), and a *lexical-to-value mapping* connecting the two. For `xsd:integer`, XSD 1.1 Part 2 §3.4.13.1 defines the lexical space as one or more decimal digits with an optional leading sign, so the strings `2` and `002` are both in it and both map to the integer two. The literal itself stores only the lexical form and the datatype IRI. The value is computed from them by the mapping, never stored as a third part, and a parser can do its whole job without ever computing it. RDF 1.1 Concepts §3.3 then defines term equality purely on the stored parts: two literals are term-equal "if and only if the two lexical forms, the two datatype IRIs, and the two language tags (if any) compare equal, character by character". Because this comparison never consults the mapping, `"2"^^xsd:integer` and `"002"^^xsd:integer` have the same value but are different terms, and since a graph is a set (as `rdf-triples-basics.md` showed), two triples differing only in those literals are two triples.

A language-tagged string is the one case with a third part. Its datatype IRI is always `http://www.w3.org/1999/02/22-rdf-syntax-ns#langString` (in the `rdf:` namespace, not `xsd:`), and N-Triples production [6] allows either a `^^` datatype or an `@` language tag after the quoted string, never both. §3.3 adds that "Lexical representations of language tags MAY be converted to lower case", so whether `@pl` and `@PL` end up as one term or two is left to each implementation. Finally, a literal whose lexical form is not in its datatype's lexical space, such as `"secret"^^xsd:integer`, is *ill-typed*: it has no value, but §3.3 states that implementations "MUST accept ill-typed literals and produce RDF graphs from them". The grammar layer only checks the shape of the literal, while checking it against a datatype belongs to a separate meaning layer, which matters because any publisher may mint a datatype IRI that no parser recognizes.

## Observable behavior

The expectation derived by hand from RDF 1.1 before running was that the simple-literal pair collapses to one triple, the integer pair stays two, the tag pair gives one or two depending only on whether the parser lowercases tags, and the ill-typed line gives one, so five or six in total. With default settings, `rdfpipe -i nt -o nt` turned the seven-line file into five output triples, a total that matched only because two per-pair differences cancelled. The simple literal `"Learner"` and the explicit `"Learner"^^xsd:string` both survived as separate lines. The pair `"2"` and `"002"` with datatype `xsd:integer` collapsed into a single triple spelled `"2"`. The pair `@pl` and `@PL` collapsed into a single triple spelled `@pl`. The ill-typed `"secret"^^xsd:integer` survived. Re-parsing with `rdflib.NORMALIZE_LITERALS = False` gave six triples: `"002"` was now preserved alongside `"2"`, the language tags were still lowercased, and a "Failed to convert Literal lexical form to value" message was logged for `"secret"` while its triple was still kept. The one-line literal-subject case, in a file whose other line was valid, failed with `rdflib.exceptions.ParserError: Invalid line: "SparQL" <http://example.com/relationship/tagged> "sparql" .`, exit status 1, and empty standard output, so the valid line was lost too.

## Internal mechanism

The pair `"2"`/`"002"` collapsed because rdflib normalizes literals of recognized XSD datatypes at construction time, which happens during parsing. It applies `xsd:integer`'s lexical-to-value mapping to `002`, gets the integer two, and replaces the lexical form with the *canonical* form of that value, which XSD §3.4.13.2 defines by prohibiting a leading `+` and leading zeroes, giving `2`. The two literals then have equal lexical forms and equal datatype IRIs, so they are term-equal, and the set keeps one triple. The pair `"Learner"`/`"Learner"^^xsd:string` did not collapse because rdflib represents a simple literal with `datatype = None` rather than with the `xsd:string` IRI, which was observed directly by inspecting both `Literal` objects. Under RDF 1.1 every literal has a datatype IRI, so this is a departure from the spec that no switch changes. The tag pair collapsed because rdflib lowercases tags, which the spec permits. The round-trip check exposed a blind spot: with normalization on, `isomorphic()` reported True between the original file and the output, because the original was itself normalized to five triples while being parsed, so both sides were already identical before the comparison ran. With normalization off it reported False (six triples against five), and a sorted diff showed exactly the `"002"` and `@PL` lines missing from the output.

## Design rationale

Normalizing by default buys convenience: literals with equal values become the same term, so deduplication and lookup by value work without extra effort. The cost is that the tool rewrites what the producer wrote, so a file that holds five or six triples under RDF 1.1 (depending only on tag lowercasing) yields five in rdflib, but a different five, with the simple-literal pair split and the integer pair merged, and the same file can yield different graphs in different tools. RDF 1.1 keeps value equality out of term equality so that the data layer reproduces exactly the terms that were exchanged, and leaves deciding that `002` and `2` "mean the same" to a separate, optional meaning layer, which is the same split that lets an ill-typed literal be accepted. A round-trip check is only as honest as its parser: if the same normalization runs on both sides, the check cannot see it, which is why the hand-derived expected set under the spec, not `isomorphic()` alone, is the reference.

## Edge cases

The ill-typed literal shows that "no value" never means "no triple". A grammar error is different in kind: it is the only place where a parser may reject input, and rdflib's N-Triples parser rejected the whole file rather than skipping only the bad line, which is a tool choice the spec does not dictate.

## Worked example

Take lines 3, 4 and 7 of `literals.nt`, the three lines with predicate `aged`, where `xsd:integer` abbreviates `http://www.w3.org/2001/XMLSchema#integer` written in full in the file. Lines 3 and 4 share subject `<http://example.com/People/Learner>` and predicate `<http://example.com/relationship/aged>`, with objects `"2"^^xsd:integer` and `"002"^^xsd:integer`. Under RDF 1.1 the lexical forms `2` and `002` differ character by character, so the objects are not term-equal and the file holds two triples here. Line 7, `"secret"^^xsd:integer`, has subject `<http://example.com/people/Learner>` with a lowercase `p`, which is a different IRI because IRIs also compare character by character, so it never collides with lines 3 and 4 and adds a third triple even though `secret` is outside the integer lexical space. The spec-derived expectation for these three lines is therefore three triples with lexical forms `2`, `002` and `secret`. The default rdflib run produced only two of them, `"2"` and `"secret"`, because `002` was mapped to the integer two and rewritten to the canonical `2` while the file was being read, making line 4 a duplicate of line 3. With normalization switched off, all three appeared, matching the hand-derived set exactly.
