# RDF Triples: IRIs, Literals, and Blank Nodes (formats)

## Overview

This exercise starts at the root of everything else in this repo: the RDF data model itself, before any query language exists. RDF stores knowledge as a pile of small, standalone statements, each saying exactly one fact, and each statement is a *triple* made of a subject, a predicate and an object. Drawn as a picture, a triple is an arrow: it starts at the subject, carries the predicate as its label, and ends at the object. The exercise was to hand-write a small dataset in N-Triples, the simplest line-based RDF serialization, where every term is spelled out in full and nothing is abbreviated, then parse it, write it back out, and check precisely what survived. This is a `formats` exercise, so no query engine was involved. The tool was rdflib 7.6.0, used through its bundled `rdfpipe` command-line tool in a disposable `python:3.12-slim` Docker container. It was chosen this time because it is actively maintained, freely licensed, and parses and re-serializes N-Triples with no glue script. The format was N-Triples as defined by the RDF 1.1 Recommendation.

## The three kinds of term

Every position in a triple holds an *RDF term*, and there are exactly three kinds of term, which RDF 1.1 Concepts §3.1 declares "distinct and distinguishable". An **IRI** is a global identifier, a string that usually looks like a web address (`<http://example.com/tech/Packer>` in N-Triples, always written in full inside angle brackets). It exists to solve a merge problem: if two publishers who never coordinate both describe a "Bob", their data must not silently fuse two different people into one node when merged. IRIs avoid this by convention rather than enforcement. An IRI is just text, nothing in RDF checks who owns the domain it names, and honest publishers simply mint IRIs only under a namespace they control. Two IRIs are the same node if and only if they are equal under simple character-by-character string comparison, so `.../alice` and `.../Alice` are two different nodes.

A **literal** is a pure value rather than an entity. It consists of a lexical form, which is a Unicode string, and a datatype IRI, with a language tag as a third element only in the language-tagged case, which a later session covers. A literal written with nothing but quotes, such as `"HashiCorp"`, is a *simple literal*, and §3.3 defines it as shorthand for the datatype `http://www.w3.org/2001/XMLSchema#string` (commonly abbreviated `xsd:string`). The quotes are part of the syntax only; the lexical form is the nine characters between them. A **blank node** is a node with no global identifier at all. In N-Triples it is written `_:` followed by a label, and §3.4 is explicit that such labels are "locally scoped to the file" and "not part of the RDF abstract syntax". Their only job is to let several lines of the same file say "this is the same unnamed node". So `_:c` in one file and `_:c` in another file are two different blank nodes.

The position rules follow from what each kind of term is. The subject must be an IRI or a blank node, the predicate must be an IRI, and the object may be any of the three. A literal cannot be a subject because a triple like `("Carol", knows, Alice)` would be a statement about the five-character string, not about any person. A predicate cannot be a blank node because a predicate is shared vocabulary. A file-local `_:knows` would mean nothing to anyone else, and after a merge two files' `_:knows` would become two unrelated relations.

## Observable behavior

The final dataset file `rdf-triples-basics/triples.nt` has ten lines. Lines six and seven are byte-identical, the literal `"HashiCorp"` is the object of both, and two blank node labels appear: `_:Adrian`, three times as a subject, and `_:HCL`, twice as an object and once as a subject. Parsing it with `rdfpipe -i nt -o nt` and printing the result produced nine lines, not ten. The line order in the output bore no relation to the order in the file. The two blank node labels were replaced by generated strings: `_:Adrian` became `_:N7ea4bca81f76401fa73aeb823056ddaa`, and `_:HCL` became `_:Nfd1b2f4f9d7946389e8e61b58047dbe8`. Every IRI and the literal `"HashiCorp"` came through character for character unchanged. The round-trip check then parsed the original file and the re-serialized file as two separate graphs. The original graph held 9 triples, the round-tripped graph held 9 triples, rdflib's `isomorphic` comparison returned `True`, and a byte comparison of the two files reported that they differ.

## Internal mechanism

The pipeline has two separate halves: text is parsed into an abstract graph, and that graph is serialized back into text. During parsing, the parser allocates a fresh blank node the first time it meets a label and reuses that same node for every later occurrence of the label in the same document, exactly as N-Triples §2.4 states. Once parsing is finished the label has done its job. The graph holds a node that is distinguishable from every other node, but no name for it, which is what "not part of the abstract syntax" means. The serializer must invent labels when writing the graph back out, and it has nothing to recover the originals from. The duplicate line also never reached the graph at all. An RDF graph is a *set* of triples (§3), so the parser's second encounter with the line-six triple added nothing, and the original graph already held only nine triples before any serialization happened. Order disappears for the same reason: a set has no order for a serializer to preserve.

## Design rationale

The right test for "did the data survive the round-trip" is graph isomorphism, not a byte comparison. RDF 1.1 Concepts §3.6 defines two graphs as isomorphic when a one-to-one mapping between their nodes exists that sends blank nodes to blank nodes, leaves every IRI and every literal exactly as it is, and turns the triple set of one graph into precisely the triple set of the other. That definition encodes exactly the freedom the mechanism above creates. Blank node labels may be renamed, provided the renaming is one-to-one so that two distinct nodes never merge, while IRIs may not change, because an IRI's exact string *is* its identity and is what lets other files link to the same node. A byte comparison would report a difference for this dataset on three independent counts (reordered lines, renamed labels, the vanished duplicate line), none of which is a change to the graph. N-Triples came first because it hides nothing: with no abbreviations, the gap between file and graph is only blank node labels, line order, and repeated lines.

## Edge cases

Two edge cases were reasoned through in dialogue but not run this session. A literal in subject position violates the position rules and should be rejected by a conforming parser, though how `rdfpipe` reports it remains unobserved. Two files that each use the label `_:c` yield two blank nodes when loaded together, not one, which follows directly from §3.4's file scoping.

## Worked example

Take the five lines of the dataset that involve `HashiCorp` and the blank node `_:HCL`. Line ten says `_:HCL <.../developedBy> <.../company/HashiCorp>`, lines eight and nine say that `<.../tech/Packer>` and `<.../tech/Terraform>` each `<.../uses>` `_:HCL`, and lines six and seven both say `<.../company/HashiCorp> <.../named> "HashiCorp"`. Reading in file order, the parser first builds the line-six triple, and on line seven it builds an identical triple and adds it to a set that already contains it, so nothing changes. It then meets `_:HCL` first on line eight and allocates a fresh node for it. On lines nine and ten it reuses that same node, so the graph now has one unnamed node that is the object of two triples and the subject of a third, which is what links the tools to the company. Across the whole file, ten lines therefore become nine triples. On serialization, rdflib wrote that blank node as `_:Nfd1b2f4f9d7946389e8e61b58047dbe8` in all three triples, and `_:Adrian`'s node as `_:N7ea4bca81f76401fa73aeb823056ddaa` in all three of its triples. That gives the isomorphism mapping directly: `_:Adrian` goes to `_:N7ea4…`, `_:HCL` goes to `_:Nfd1b…`, and every IRI and the literal `"HashiCorp"` go to themselves. Under that mapping each of the nine original triples corresponds to exactly one output triple, which is why the isomorphism check returned `True` even though the two files differ byte for byte.
