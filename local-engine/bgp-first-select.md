# Basic Graph Patterns: A First SELECT Query (local-engine)

## Overview

This is the first exercise in this repo that queries data rather than only parsing it. Up to now the two `formats` sessions treated an RDF graph as something to write down and read back. Here the same kind of graph is loaded into a running SPARQL engine, and questions are put to it. The intuition is simple: take a triple, and replace one or more of its three positions with a placeholder that means "I don't know this part yet". The engine then looks for every triple in the graph that fits, and reports what the placeholders would have to be for each fit. The exercise was a seven-line N-Triples dataset written by hand and six queries, all written with full `<IRI>`s and no prefixes. Q1 has one unknown, Q2 has two unknowns, Q3 joins two patterns through a shared unknown, and Q4a–c test how a constant integer literal matches. The target is `local-engine`, using Oxigraph 0.5.11 (image `ghcr.io/oxigraph/oxigraph:0.5.11`), run in memory in a disposable container and queried over the SPARQL 1.1 Protocol. It was chosen by a live lookup as an actively maintained, Apache-2.0/MIT-licensed, complete SPARQL 1.1 store with an official prebuilt image and a documented `--explain`/`--stats` query plan. Apache Jena Fuseki was the runner-up, but its docs offer a Dockerfile to build rather than an official prebuilt image.

## Variables, triple patterns, and solutions

A *query variable* is a name written `?x`. A *triple pattern* is a triple in which any position may be a variable instead of an RDF term, and a set of triple patterns inside `WHERE { }` is a *basic graph pattern* (BGP). A data triple matches a triple pattern when every constant position holds exactly the same RDF term and each variable position holds any term at all. "Exactly the same" reuses the equality rules from earlier sessions: IRIs compare character by character (`rdf-triples-basics.md`), and literals compare on lexical form, datatype IRI and language tag together (`rdf-literal-datatypes.md`). Each way the BGP can match gives one *solution*, which SPARQL 1.1 §18.1.8 defines as "a partial function μ : V -> RDF-T", that is, a mapping from variable names to terms rather than a positional tuple. A variable that the mapping assigns a term to is *bound* to that term. When a variable appears in several triple patterns, it must be bound to the same term in all of them within one solution, and this implicit join is the core mechanism of a BGP. `SELECT` then *projects* each finished solution onto the variables it lists. The result is a solution sequence, "possibly unordered" (§18.1.8), so without `ORDER BY` any order is correct, and comparing a prediction with a result means comparing them as multisets.

## Observable behavior

Every expected result was derived by hand from `data.nt` before the run and compared field by field with the SPARQL JSON results (`head.vars`, `results.bindings`, and per-term `type` and `value`). Q1 (Alice `worksAt` `?name`) returned one solution, binding `?name` to the IRI `http://example.com/company/Tentris`. Q2 (`?person worksAt ?name`) returned three solutions: Bob with HashiCorp, Alice with Tentris, and a `bnode` with value `ec9d32f6a7cf1995ed6abda42259de1` with Tentris. The rows came back with the blank node first, which was a different order from the prediction, and that is acceptable because there is no `ORDER BY`. Q3 returned two solutions, a `bnode` (same label) with `http://example.com/tech/SparQL` and Alice with SparQL, and Bob was absent. Q4a (`"2"^^xsd:integer`), Q4b (`"002"^^xsd:integer`) and Q4c (bare `2`) each returned the same single solution, the blank node. A `GET /store?default` dump of the whole store showed six triples, not seven, with only one `aged` triple, spelled `"2"^^xsd:integer`.

## Internal mechanism

Oxigraph's `query --explain --stats`, run on a separate on-disk store loaded once from the same file, showed the plan for Q3 as `Project(?person, ?technology)` over `Lateral` over two `QuadPattern` nodes. The `worksAt` pattern produced 3 results, and the `develops` pattern reported 2. `Lateral` means that for each solution from the first pattern, the engine evaluates the second pattern with `?employer` already substituted. The second pattern therefore ran three times: Tentris (from Alice) matched one triple, HashiCorp (from Bob) matched none, and Tentris (from the blank node) matched the same triple again. That gives 2 in total, and shows that one data triple can contribute to several solutions. `Project` sits above the join, so it removes `?employer` only from solutions that are already complete, after `?employer` has done its linking work. Adding `?employer` to `SELECT` would change the columns but not the number of rows. For Q4, the dump shows that Oxigraph rewrote `"002"` to its canonical form `"2"` during loading, after which the two `aged` triples were identical and the set kept one. That Q4b, whose constant is `"002"`, still matched a store holding only `"2"` shows that the query constant was also handled by value, either canonicalized when the query was parsed or compared by value during matching. These two possibilities cannot be told apart from outside, and no Oxigraph documentation found during the session states which one it is.

## Design rationale

Q3 is written as one BGP with a shared variable rather than as two separate queries joined afterwards by the client. For IRIs a client-side join would work, because IRIs are global. For blank nodes it would not be reliable: §2.4 says blank node labels "are scoped to a result set", so a label from one query's result has no guaranteed relation to the same label in another query's result. Oxigraph happened to reuse `ec9d32f6...` across Q2, Q3, Q4 and the dump, but that is a property of this engine and nothing a portable client may rely on. Keeping the join inside one BGP lets the engine join on the actual nodes rather than on their printed labels. Writing every IRI in full was a deliberate pacing choice: a full-IRI triple pattern is just an N-Triples line with some positions replaced by variables, and the Turtle-style abbreviations SPARQL borrows (`PREFIX`, `;`, `,`, `a`) are left to their own session.

## Edge cases

Q4 is the case where this engine departs from strict term matching. §2.3.3 says a typed literal matches "because the lexical form and datatype IRI both match", which, applied to the file as written, would give Q4a only the `"2"` line and Q4b only the `"002"` line. Oxigraph's load-time canonicalization makes both return the same single triple, which is the same normalization `rdf-literal-datatypes.md` observed in rdflib, now in a second tool. Blank node scope showed up through an infrastructure mistake. When `data.nt` was accidentally loaded twice into the on-disk explain store, Q3 returned three rows, with Alice once and two distinct blank nodes, because each load maps `_:Employee1` to a fresh node. The IRI triples from the second load were identical to the first and merged, but the blank-node triples were new triples.

## Worked example

Take the four triples Q3 can touch: Bob `worksAt` HashiCorp, Alice `worksAt` Tentris, `_:Employee1` `worksAt` Tentris, and Tentris `develops` SparQL, all with the full `http://example.com/...` IRIs written in `data.nt`. The first pattern, `?person worksAt ?employer`, matches the three `worksAt` triples, giving three partial solutions: (Bob, HashiCorp), (Alice, Tentris) and (blank node, Tentris). For each one the second pattern, `?employer develops ?technology`, is evaluated with `?employer` fixed. With HashiCorp no `develops` triple has that subject, so Bob's partial solution is discarded. With Tentris, the single `develops` triple matches and binds `?technology` to SparQL, and this happens twice, once for Alice and once for the blank node. Projection to `?person ?technology` then drops `?employer`, leaving exactly two solutions, (Alice, SparQL) and (blank node, SparQL), in which every bound term is an IRI apart from the blank node itself. That is what the engine returned, with the blank node labelled `ec9d32f6a7cf1995ed6abda42259de1` rather than `Employee1`, and listed first.
