# FILTER and Three-Valued Logic over Unbound Variables (local-engine)

## Overview

`optional-unbound.md` established that an `OPTIONAL` can leave a variable unbound, meaning the solution mapping simply has no pair for it. It left one question open: what happens when such a variable is used in a comparison. This exercise answers it with `FILTER`. A filter does not match triples. It takes the solutions that a group's patterns have already produced, evaluates an expression for each one, and keeps only those where the expression is true. The interesting part is that a SPARQL expression has three possible outcomes, true, false or error, and an unbound variable is the most common way to get the third. The dataset is a hand-written six-triple Turtle file about four people, `data.ttl`, queried by six user-written queries, `q1-baseline.rq` to `q6-pattern-constant.rq`. The target is `local-engine` with Eclipse RDF4J Server 6.0.1 (image `eclipse/rdf4j-workbench:6.0.1-jetty`), using an in-memory repository in `STRICT` evaluation mode, queried over the SPARQL 1.1 Protocol. It replaced Oxigraph, used in both previous local-engine sessions, because it was the comparison engine named in the OPTIONAL session and because `bgp-first-select.md` had shown Oxigraph rewriting `"002"^^xsd:integer` to `"2"` on load, which would have hidden the term-versus-value contrast this session needed. That makes this session also the first cross-engine comparison in the repo.

## Filters, scope and errors

The spec's §5.2.2 says a filter "is a restriction on solutions over the whole group in which the filter appears". Where the `FILTER` is written inside the `{ }` therefore does not matter. All four filter queries here (`q2` to `q5`) put it first, before any triple pattern has bound anything. That is still correct, because the group's patterns, including the `OPTIONAL`, produce their solutions first, and the filter is applied to that finished set afterwards.

§17.2 then defines what an expression produces. Every function and operator except `BOUND`, `COALESCE`, `EXISTS` and `NOT EXISTS` raises a type error when an argument is unbound, and any expression other than `||` and `&&` passes an error through unchanged. So `!E` is still `E`. The two logical connectives are the exception. `T || E` is `T` and `F && E` is `F`, because the other side already decides the answer. `F || E` and `T && E` remain `E`. Finally, "FILTERs eliminate any solutions that … either result in an effective boolean value of false or produce an error". There are two distinct levels here. The expression collapses to a single value per solution, and the filter keeps that solution only if the value is `T`.

A second error source matters for comparisons between incompatible literals. The §17.3 operator table chooses a row for `A != B` by the operand types. When there is no numeric/numeric or string/string row, it falls back to `fn:not(RDFterm-equal(A, B))`. §17.4.1.7 says `RDFterm-equal` "produces a type error if the arguments are both literal but are not the same RDF term". A string compared with an integer is therefore neither equal nor unequal. It is an error.

## Observable behavior

The N-Triples dump of the repository after loading showed all six triples, with Alice's age stored exactly as written, `"020"^^xsd:integer`. RDF4J did not canonicalize it. `q1-baseline.rq` (required `aged`, optional `experienced`) returned four solutions. Bob had age 46 and years `"10"^^xsd:integer`, Ben had age 21 and years `"2 years"` (a plain `xsd:string`), and Alice and James had no `"years"` key in their JSON binding objects. `q2-filter-neg.rq`, with `FILTER(?years != 10)`, returned an empty `bindings` array. `q3-filter-bound.rq`, with `FILTER(!bound(?years) || ?years != 10)`, returned exactly Alice and James. Its TSV rendering printed Alice's age as `20`, while the JSON rendering of the same query kept `"020"`. `q4-eq.rq`, with `FILTER(?age = 20)`, returned only Alice, and her binding was still `"020"^^xsd:integer`. `q5-same-term.rq`, with `FILTER(sameTerm(?age, 20))`, returned no solutions, and so did `q6-pattern-constant.rq`, which writes `20` directly as the object of the `aged` triple pattern.

## Internal mechanism

For the filter queries, the group is evaluated as a filter over a left join. The required `aged` pattern produces four mappings over `?person` and `?age`. The left join from `optional-unbound.md` extends Bob's and Ben's mappings with a `?years` pair and leaves Alice's and James's unchanged. The filter is then evaluated once per mapping, and projection comes last. In `q2`, Bob gives `10 != 10`, which is `F`. Alice and James give `E`, because `?years` is unbound. Ben gives `E` too, because `"2 years"` and `10` are two literals that are not the same term. All four are dropped. In `q3`, `!bound(?years)` never errors, so the left side is always `T` or `F`. That lets `||` rescue exactly the unbound rows and nothing else.

For `q4` to `q6`, the operator table again decides the outcome. Both operands of `?age = 20` are numeric, so the numeric row applies and calls `op:numeric-equal`, which compares values: 20 equals 20 even though the stored lexical form is `020`. `sameTerm` compares terms, which `rdf-literal-datatypes.md` established means lexical form plus datatype IRI, so `"020"` is not `"20"`. A constant in a triple pattern is also matched as a term, which is why `q6` behaves like `q5` and not like `q4`. RDF4J's query plan was not inspected (its docs describe explain as unsupported over a remote server), so the mechanism here is the spec algebra.

## Design rationale

`q2` and `q3` ask two genuinely different questions. `q2` asks for people known to have experience other than 10, so a missing value counts as unknown and is excluded. `q3` asks for people not known to have exactly 10 years, so a missing value counts as "not 10". The user's own rewrite, `!(bound(?years) && ?years = 10)`, expresses the same second meaning and gives the same four outcomes: `F && E = F` for Alice, which the `!` turns into `T`, and `T && E = E` for Ben. If SPARQL silently treated an unbound comparison as true or false, it would have to pick one of these meanings on the query writer's behalf, and `?years = 10` and `?years != 10` could no longer both be "not true" for a missing value. Making it an error keeps the two operators consistent and forces an explicit `bound` guard. Choosing `=` or `sameTerm` is the same kind of decision for literals: value or exact stored spelling.

## Edge cases

Three edge cases surfaced. First, `q6` gives an empty result on RDF4J, while `bgp-first-select.md` recorded a query constant `2` finding data written as `"002"` on Oxigraph. The difference is in the store, not in pattern matching: Oxigraph had already rewritten the term to `"2"` on load, so its match was also a term match. Second, a bound but incompatible value (Ben's string) fails a `!=` filter just as surely as an unbound one, so "bound" is not enough to guarantee a true or false comparison. Third, RDF4J's TSV writer printed `"020"^^xsd:integer` as the bare `20`, while JSON kept the lexical form. That is a result-format behavior this session observed but did not explain.

## Worked example

Take the dataset's four solutions after the left join, exactly as `q1` returned them. Bob is `{?person → ppl:Bob, ?age → 46, ?years → 10}`, Alice is `{?person → ppl:Alice, ?age → "020"^^xsd:integer}`, Ben is `{?person → ppl:Ben, ?age → 21, ?years → "2 years"}` and James is `{?person → ppl:James, ?age → 16}`. Now evaluate the `q3` expression `!bound(?years) || ?years != 10` for each one.

For Bob, `?years` is bound, so `!bound(?years)` is `F`. `10 != 10` uses the numeric row and is `F`, and `F || F` is `F`, so Bob is dropped. For Alice, there is no `?years` pair, so `!bound(?years)` is `T`. `?years != 10` raises a type error because its argument is unbound, but `T || E` is `T`, so Alice is kept. James follows exactly the same path as Alice and is kept. For Ben, `?years` is bound, so the left side is `F`. On the right, `"2 years"` is a string and `10` is an integer, so the table falls back to `fn:not(RDFterm-equal(...))`. Two different literals make `RDFterm-equal` raise an error, and `fn:not` passes it through, so the right side is `E`. `F || E` is `E`, so Ben is dropped. The filter keeps only `T`, so the result is Alice and James, with `?years` absent from both. That is exactly what RDF4J returned; without the guard, as in `q2`, both become `E` and the result is empty.
