# DISTINCT and Duplicate Solutions after Projection (local-engine)

## Overview

A graph is a set: `rdf-turtle-abbreviations.md` showed that writing the same triple twice still gives one triple. A query result can nevertheless contain the same row twice, and this exercise looks at where those duplicates come from and what `DISTINCT` and `REDUCED` do about them. The duplicates do not come from the data. They come from projection. Two solutions that differ only in a variable the `SELECT` clause drops become identical once that variable is removed, and SPARQL keeps both copies. The dataset is the user's `data.ttl`, reused from `modifier-order-slice` with Carol removed and new triples added. The part that matters is five `rel:worksAt` triples. Bob works at `cmp:ID5` and `cmp:Tentris`, Alice at `cmp:Tentris`, and James at `cmp:Microsoft` and at a blank node. Two integer probes, `rel:jumps "09"^^xsd:integer` on Ben and `rel:jumps "9"^^xsd:integer` on James, were added to test whether DISTINCT compares terms or values. Five user-written queries, `q1.rq` to `q5.rq`, all match `?person rel:worksAt ?employer` and project only `?employer`. They differ only in their modifiers.

The target is `local-engine` and the engine was QLever (`adfreiburg/qlever:latest`). A fresh live lookup picked it as actively maintained, claiming full SPARQL 1.1 support with automated W3C conformance runs, and a sixth engine for the repo. The deciding reason was that its own `application/qlever-results+json` response includes the executed operator tree, which makes the internal mechanism observable. QLever does not load data over HTTP. Instead, `qlever-index` built an index from `data.ttl` inside a named volume, and `qlever-server` then served it on port 7001.

## Bags, cardinality and the modifier pipeline

A *multiset*, or bag, is a collection in which the same element may occur more than once. The number of times a given solution occurs is that solution's *cardinality*. Matching a basic graph pattern against a graph gives each solution cardinality 1. §18.2.5, quoted in `modifier-order-slice.md`, then applies OrderBy, Project, Distinct, Reduced and Slice in that order. Project restricts every solution to the selected variables and maps each solution to exactly one restricted solution. So it never changes the length of the sequence, and projected solutions that become identical simply add up their cardinalities. §15.3.1 says "Only one solution solution that binds the same variables to the same RDF terms is returned" (the doubled word is in the spec). The comparison is between terms, not values. §18.5 defines Distinct with card 1 for every solution and requires it to preserve "any ordering given by OrderBy". §15.3.2 says REDUCED only "permits" duplicates to be eliminated. Each solution's cardinality may be anything from 1 up to its cardinality without the modifier.

## Observable behavior

The store dump, a `CONSTRUCT` of every triple requested as N-Triples, returned 16 triples, matching the file and the index log. However, Ben's and James's `rel:jumps` values both came back as `"9"^^<http://www.w3.org/2001/XMLSchema#int>`, and every `rel:age` was likewise `xsd:int`. `q1.rq` (no modifier) returned five rows: Tentris, ID5, Tentris, Microsoft and a blank node labelled `bn1` with type `bnode`. That is Tentris at cardinality 2. `q2.rq` (`select distinct`) returned four rows: ID5, Microsoft, Tentris, `bn1`. `q3.rq` (`distinct`, `order by ?person ?employer`, `offset 4`) returned an empty bindings array. `q4.rq` (the same with `limit 2`) returned Tentris, then ID5. `q5.rq` (`select reduced`) returned the same five rows in the same order as `q1.rq`. Each result matched the user's hand-derived expectation. For `q5.rq` the expectation was the set of allowed totals {4, 5}.

## Internal mechanism

QLever's execution trees explain the row orders. QLever stores every triple in several sorted *permutations*, named for their sort order: SPO, SOP, PSO, POS, OSP and OPS. `q1.rq` ran as a single `IndexScan PSO`. With the predicate fixed, that scan returns rows in subject order: Alice's Tentris, Bob's ID5 and Tentris, then James's Microsoft and blank node. That explains q1's order, which looks arbitrary but isn't. `q2.rq` ran as `Distinct` over an `IndexScan POS`, with no Sort node. A POS scan with the predicate fixed returns rows in object order, which here is `?employer` order. Equal employers therefore arrive next to each other, and Distinct removes them in one pass that compares each row only with the previous one. The sorted-looking output is a side effect of that scan, not a guarantee. `q3.rq` and `q4.rq` ran as `IndexScan POS`, then `Distinct`, then `OrderBy ASC(?person) ASC(?employer)`, then the slice. QLever deduplicated *before* sorting, the reverse of the spec's OrderBy-then-Distinct, and it kept `?person` as a hidden column through Distinct. `q5.rq` produced exactly `q1.rq`'s tree. QLever used REDUCED's permission to do nothing at all.

## Design rationale

DISTINCT is what a query needs when duplicates must be absent. Its cost is a full sort or a hash over every solution whenever the input order does not already match the projected variables. REDUCED tells the engine that duplicates are harmless downstream. That lets the engine skip that work, and when the input happens to be sorted it can still drop adjacent duplicates almost for free. The user's own judgement was that a client which must deduplicate anyway gains little from REDUCED. Writing neither modifier is right when multiplicity carries information, as in `q1.rq`, where Tentris appearing twice records two employees. The design rule taken from `q4.rq` is to avoid ordering by a variable that DISTINCT projects away. When LIMIT is involved, projecting the sort keys keeps the result well defined.

## Edge cases

§18.5 defines Distinct as `[ μ | μ in Ψ ]` with cardinality 1 and order preserved, but it never says *which* of two equal solutions survives. In `q4.rq` the projected sequence has Tentris at positions 1 and 3. Keeping position 1 gives Tentris, ID5 under `limit 2`. Keeping position 3 gives ID5, Tentris: the same rows in the opposite order. QLever's agreement with the first-occurrence reading is a coincidence. Within one object, POS lists subjects in ascending order, the same direction as `order by ?person`, so the Tentris row it kept, Alice's, is also the one that sorts first. Nothing documented guarantees this. A second edge case is QLever's integer handling, which its compliance page documents. It turned `"09"^^xsd:integer` into `"9"^^xsd:int`, which is a different term in both lexical form and datatype. The dump came from a plain CONSTRUCT, so the merge happened before any DISTINCT ran, at load time or in the output serializer. As a result, the integer probe cannot show on this engine whether DISTINCT compares terms or values. Finally, REDUCED has no single expected result. Verification here was membership in an allowed set, the first time this repo needed that.

## Worked example

Take the five `rel:worksAt` triples: `ppl:Bob rel:worksAt cmp:ID5`, `ppl:Bob rel:worksAt cmp:Tentris`, `ppl:Alice rel:worksAt cmp:Tentris`, `ppl:James rel:worksAt cmp:Microsoft`, and `ppl:James rel:worksAt _:b`. The query is `q4.rq`: `select distinct ?employer where { ?person rel:worksAt ?employer . } order by ?person ?employer limit 2`. Matching yields five solutions, each with cardinality 1. OrderBy sorts them by `?person` and then by `?employer`, and §15.1 ranks a blank node before an IRI. The sequence is therefore (Alice, Tentris), (Bob, ID5), (Bob, Tentris), (James, `_:b`), (James, Microsoft).

Project drops `?person` and leaves Tentris, ID5, Tentris, `_:b`, Microsoft. This is still five entries, and Tentris now has cardinality 2. Distinct keeps one Tentris, and reading it as keeping the first occurrence leaves Tentris, ID5, `_:b`, Microsoft. Slice with `limit 2` keeps the first two, so the expected result is Tentris then ID5. QLever returned exactly Tentris then ID5. It got there by a different route: the POS scan delivered (ID5, Bob), (Microsoft, James), (Tentris, Alice), (Tentris, Bob), (`bn1`, James). Distinct dropped Bob's Tentris row as the second of an adjacent pair, OrderBy then sorted the four survivors by the hidden `?person` column, and the limit kept Alice's Tentris and Bob's ID5.
