# ORDER BY with LIMIT and OFFSET: Ordered Slices of a Solution Sequence (local-engine)

## Overview

`bgp-first-select.md` established that a query's result is a solution sequence that is "possibly unordered": without `ORDER BY`, any order is correct. This exercise is the first one in the repo that asks for an order. It then cuts a page out of the ordered sequence with `LIMIT` and `OFFSET`. Underneath it is a simple question: what has to be true for "rows 3 to 3" to mean the same row every time? The answer comes in two parts. First, the spec has to define how every pair of compared values is ordered. Second, the sort keys taken together must never tie. The dataset is a hand-written Turtle file, `data.ttl`, about five people. Bob and Carol have no `rel:age`, Alice's `rel:age` is a blank node, and Ben and James have the integers 9 and 16. The four user-written queries `q1.rq` to `q4.rq` all share one pattern, a required `rel:name` with an optional `rel:age`, and differ only in their solution modifiers.

The target is `local-engine`, and two engines ran side by side. The first was Virtuoso Open Source 7.2.17 (`openlink/virtuoso-opensource-7:7.2.17`). A fresh live lookup picked it as a mainstream, actively maintained, freely available engine (image pushed 2026-08-05), and a fourth engine after Oxigraph, RDF4J and Fuseki. The data was loaded with isql's `DB.DBA.TTLP` into the named graph `urn:ex:modifier-order-slice`, and queries were sent with the protocol's `default-graph-uri` parameter. The second was Tentris v1.3.0 (`ghcr.io/tentris/tentris:v1.3.0`, the non-commercial edition), which the user proposed as an independent cross-check. A live lookup showed it was released on 2026-10-01 and is free for non-commercial use, but it is proprietary and much less widely deployed than the earlier three engines. The data was loaded with a Graph Store Protocol `PUT` into the default graph. Both dumps matched the file triple for triple.

## How SPARQL orders RDF terms

§15.1 gives two kinds of rule. The first is a fixed ranking between kinds of term: no value (an unbound variable) sorts lowest, then blank nodes, then IRIs, then literals. The second is the `<` operator, which orders a *pair* of numerics, a pair of simple literals or `xsd:string`s, and a few other same-typed pairs. Pairs of IRIs are compared as simple literals. String comparison works one character at a time from the left and stops at the first difference, so `"10"` sorts before `"9"` because `'1'` is less than `'9'`, whereas the integer 9 sorts before 10. `rdf-literal-datatypes.md` covered the difference between a literal's lexical form and its value; ordering is where that difference becomes visible. The spec explicitly does not define a total order. For example, the order of a simple literal against an `xsd:integer` is undefined. That is why the dataset gives each sorted variable values of one type only. A sort column mixing `"9"` and 10 would have had no fully derivable expected order. Each `ORDER BY` comparator is applied in turn. The next comparator is consulted only when the earlier ones "produce the same RDF term", and when every comparator ties, the order of the two rows is undefined.

## Observable behavior

On the four-person dataset (before Carol was added), `q1.rq` (`order by ?age`) returned Bob (unbound), Alice (blank node), Ben (9), James (16) on Tentris, exactly as derived by hand. Virtuoso returned Bob, Alice, James (16), Ben (9), reporting both ages as `xsd:integer` in its JSON. `q2.rq` (the same plus `limit 1 offset 2`) returned Ben, 9 on Tentris and James, 16 on Virtuoso. `q3.rq` (`order by ?name`, with `?name` not projected) returned Alice, Ben, Bob, James on both engines. After Carol was added, giving 16 triples on both engines, `q1.rq` returned Carol before Bob on Tentris and Bob before Carol on Virtuoso. `q4.rq` (`order by ?age ?name limit 1`) returned Bob on both, and `q2.rq` returned Alice on both. An earlier version of the user's `q1.rq` said `select ?person, ?age`. Virtuoso accepted the comma; Tentris rejected it with `Parse Error: mismatched input ','` and HTTP 400.

## Internal mechanism

§18.2.5 fixes the pipeline. Pattern matching produces a multiset, an unordered bag of solutions. `ToList` gives it a sequence shape with "no implied ordering". Then come `OrderBy`, `Project`, `Distinct`, `Reduced` and finally `Slice(M, start, length)`. Two consequences follow. Because `Project` comes after `OrderBy`, a query can sort on a variable it does not select, which is what `q3.rq` does with `?name`. Because `Slice` comes after `OrderBy`, `OFFSET 2` means "skip the first two solutions of the *ordered* sequence". Without `ORDER BY`, the slice cuts a sequence whose order was never fixed, so `q2.rq` without its `ORDER BY` could return any one of the four people. Virtuoso's swap of Ben and James is not undefined behavior: two `xsd:integer`s are a defined pair, so its order is a conformance bug. Diagnostic probes on Virtuoso narrowed it down. Sorting only the two integer rows still gave the wrong order, so the blank node and unbound rows were not involved. The projected expression `?age < 10` evaluated correctly, so the engine's `<` itself compares these values numerically. `ORDER BY (?age + 0)` and a `VALUES` list `{ 16 9 }` both sorted correctly. So the fault appears only when the engine sorts the stored term directly. No official Virtuoso document explaining the cause was found.

## Design rationale

`q4.rq` adds `?name` because sorting by `?age` alone leaves Bob and Carol tied. A tie lets the engine choose, and the two engines did choose differently. With `LIMIT 1`, a page built on a tie can return a different person from one engine, version or run to the next. A second comparator that is consulted only on a tie makes this dataset's order total. In general, the keys taken together must be unique per solution, and `?name` is not: a second person named "Bob" would tie again. Adding `?person` last guarantees uniqueness here, because IRIs are compared as simple literals and every row has a different person. A server-side cap such as Virtuoso's `ResultSetMaxRows` (commented out at 100000 in this container's `virtuoso.ini`) is not a substitute. It protects the server by acting as an unordered limit, and it offers no "start after N", so it cannot support paging.

## Edge cases

A tie matters only when a slice boundary falls inside it. On the five-person data, `q2.rq` skips exactly the two tied rows, Bob and Carol, so whichever order they come in, the third row is Alice. Both engines returned Alice even though they ordered the tie oppositely in `q1.rq`. The same effect hid Virtuoso's integer bug: `q2.rq` and `q4.rq` on the five-person data stop before reaching Ben and James, so a slice can conceal an ordering defect as easily as reveal one. A blank node as an "age" is semantically odd, but RDF allows it, and it was included only to exercise the blank-node rank.

## Worked example

Take the final `data.ttl`. Bob and Carol each have only a `rel:name`. Alice has `rel:name "Alice"` and `rel:age []`. Ben has `rel:age 9` and James `rel:age 16`, both read by Turtle as `xsd:integer`. The required pattern `?person rel:name ?name` matches all five people, and the `OPTIONAL { ?person rel:age ?age }` extends Alice, Ben and James, leaving Bob and Carol with `?age` unbound, as `optional-unbound.md` describes. `ToList` turns these five solutions into a sequence in no particular order.

`q4.rq` sorts by `order by ?age ?name`. The first comparator ranks Bob and Carol, both unbound, below Alice's blank node, which ranks below the two integers, and `<` puts 9 before 16. Bob and Carol produce no distinct term on `?age`, so the second comparator decides between them. `"Bob"` and `"Carol"` are simple literals and differ at the first character, `'B'` against `'C'`, so Bob comes first. The ordered sequence is therefore Bob, Carol, Alice, Ben, James, and every pair in it is defined. `Project` then drops `?name`, and `Slice(M, 0, 1)` keeps the first solution. The predicted result is one row, `?person = ppl:Bob` with `?age` unbound, and both Tentris and Virtuoso returned exactly that. Removing `?name` from the sort, as in `q1.rq`, leaves the first two positions undefined. Tentris then put Carol first and Virtuoso put Bob first, both within the spec.
