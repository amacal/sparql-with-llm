# ASK and CONSTRUCT: Query Forms Beyond SELECT (local-engine)

## Overview

Every earlier exercise used `SELECT`, which returns a table of solutions. SPARQL 1.1 §16 names three other query forms, and this exercise covers two of them. `CONSTRUCT` returns a new RDF graph built from a template, and `ASK` returns a single boolean saying whether the pattern has any solution. Seven hand-written queries over an 18-triple people dataset (`data.ttl`) cover the template rules from §16.2: identical instantiated triples collapse by set union, a template blank node is minted fresh for each solution, and a template triple with an unbound variable or a literal subject is dropped. They also cover the restriction of the `CONSTRUCT WHERE` short form to a basic graph pattern, and `ASK` and `SELECT *` over a pattern with no variables. The target is `local-engine`. The primary engine was Oxigraph 0.5.12 (`ghcr.io/oxigraph/oxigraph:0.5.12`, in memory, loaded over its Graph Store endpoint). The plan agent's live lookup on 2026-10-19 picked it because it was a newly released version not yet exercised here, because its `/store?default` dump checks the loaded data without relying on a CONSTRUCT, and because its CLI prints an evaluation plan with `--explain`.

## How CONSTRUCT and ASK are defined

§16.2 defines the CONSTRUCT result as the graph obtained by "taking each query solution in the solution sequence, substituting for the variables in the graph template, and combining the triples into a single RDF graph by set union". The same paragraph says an instantiation that contains an unbound variable, or that would put a literal in subject or predicate position, "is not included in the output RDF graph". §16.2.1 adds that a blank-node label written in the template is scoped to one solution: one fresh node per solution, shared by every template triple of that solution. §16.2.4 allows `CONSTRUCT WHERE { … }` only when the pattern is a basic graph pattern. §16.3 says `ASK` returns "just whether or not a solution exists", which Results-JSON §4 writes as a `"boolean"` member. The set view of a graph is reused from `formats/rdf-triples-basics.md`, where a duplicated triple line adds nothing to the parsed graph. The meaning of an unbound variable, a pair absent from the mapping, is reused from `local-engine/optional-unbound.md`.

## Engine panel outcomes

The silent panel was Apache Jena Fuseki 6.2.0 (built from the official `jena-fuseki-docker-6.2.0` kit), Eclipse RDF4J 6.1.0, QLever (digest `sha256:1ef17d17…`), Tentris v1.4.0, and Virtuoso Open Source 7.2.17 (loaded into the named graph `urn:form-ask-construct:ds` and queried with `default-graph-uri`). GraphDB was excluded because even its free edition needs a registered license file. All six engines stored the 18 triples, although QLever stored the three ages as `xsd:int`. On q1, RDF4J and QLever wrote four N-Triples lines that parse to the same two triples the others sent. QLever's source sets `construct-deduplication` to no deduplication by default. All six agreed on q2 (9 triples, 4 blank nodes), q5 (`true`) and q6 (`false`). On q3, Oxigraph and RDF4J returned the six legal triples, Tentris wrote seven lines that parse to the same six triples, and Fuseki returned ten triples, four of them with a literal subject. QLever returned eleven lines making the same ten triples, and Virtuoso answered HTTP 500 with "RDF01 Error Bad variable value in CONSTRUCT". On q4, five engines rejected the illegal short form with HTTP 400. Virtuoso accepted it and returned seven triples, treating the `OPTIONAL` as required. On q7, Oxigraph, Fuseki, RDF4J and QLever returned `"vars": []` with `"bindings": [{}]`, Tentris answered HTTP 500, and Virtuoso invented a variable `_star_fake` bound to `"1"^^xsd:integer`.

## Observable behavior

q1 used the template `ppl:Bob rel:at ?name` over a `UNION` of Bob's `rel:worksAt` and `rel:employeeOf`, which produced four solutions. Oxigraph returned two triples, `ppl:Bob rel:at cmp:Tentris` and `ppl:Bob rel:at cmp:ID5`, in that order, with `content-type: application/n-triples` because the request's `Accept` header asked for that format. The order carries no meaning, since the result is a set. q3 used the template `?person rel:name ?name . ?name rel:at ?employer` with an `OPTIONAL` on `rel:worksAt`. Oxigraph returned six triples, one `rel:name` triple per named subject including the Oracle blank node. No `rel:at` triple survived, because `?name` is always a literal. q5 returned `{"head":{},"boolean":true}` and q6, which asks about `cmp:IBM`, returned `false`.

## Internal mechanism

§18.1.10 defines an abstract query as a tuple of an algebra expression E, a dataset DS and a query form QF, and this is directly visible in Oxigraph's plan. For q3, `query --explain` printed `Project(?employer, ?name, ?person)` over a `ForLoopLeftJoin` of two `QuadPattern`s. Neither `rel:at` nor any template triple appears anywhere in the plan. The template is applied by QF after E has produced its solution sequence. Each solution is substituted into the template, any instantiated triple containing an unbound variable or an illegal term is dropped, and the remaining triples are set-unioned. ASK, SELECT and CONSTRUCT over the same pattern share E and differ only in QF. Set union constrains the graph, not the text that serializes it. An N-Triples document represents "exactly each triple matching" its lines (N-Triples §1), so four lines that repeat two triples still represent the correct two-triple graph. An engine that streams one instantiated triple per solution, as QLever does by default, conforms while sending redundant bytes.

## Design rationale

CONSTRUCT is the right form when the output must itself be RDF, to be loaded, merged or reserialized. SELECT is the right form when the solution table is wanted, including which variables are unbound. Silently dropping an untransformable triple treats an illegal term the same way as an unbound variable. RDF does not fix what kind of term a property's object is: `rel:employeeOf` points to an IRI for Bob and to a blank node for Monica, and another dataset could give it a literal. So one template can be legal for some solutions and not others, and a single odd solution never spoils the graph built from the rest. The cost showed up in q3: a template bug produced nothing and no conforming engine reported it. Virtuoso chose the opposite trade-off and failed the whole query. Fuseki and QLever made neither choice and emitted triples that are not RDF. Fed to a fresh Oxigraph, Fuseki's q3 body failed at line 1 with "The subject of a triple must be an IRI or a blank node" and stored nothing. The short-form restriction is different in kind: an `OPTIONAL` inside `CONSTRUCT WHERE` is wrong whatever the data, so it can be rejected before any data is read.

## Edge cases

A pattern with no variables that matches has exactly one solution, the empty mapping `{}`. That is why q5 is `true` and why q7's `SELECT *` must return `"vars": []` with one empty binding, not zero bindings. Blank-node labels in a CONSTRUCT response are scoped to that response. Oxigraph happened to print Monica's employer as `_:bf30a224…` both in the store dump and in q2's output, but that reuse is an implementation detail. Within one response, the only requirements are that one node keeps one label wherever it appears and that distinct nodes get distinct labels; which label text is used is the engine's choice.

## Worked example

The relevant triples of `data.ttl` are Bob's `rel:name "Bob"`, `rel:worksAt cmp:ID5` and `rel:worksAt cmp:Tentris`, and Monica's `rel:name "Monica"` and `rel:employeeOf` pointing to a blank node, here called `_:m`. The query q2 has the template `?person rel:at ?name . ?person rel:id _:random . _:random rel:belongsTo ?person` and a WHERE that unions Bob's `rel:worksAt` with Monica's `rel:employeeOf`, each branch also matching `?person rel:name` against the person's name. The WHERE yields three solutions: `?person` bound to Bob with `?name` bound to `cmp:ID5`, Bob again with `cmp:Tentris`, and Monica with `_:m`. Instantiating the first solution gives `ppl:Bob rel:at cmp:ID5`, `ppl:Bob rel:id _:r1` and `_:r1 rel:belongsTo ppl:Bob`, where `_:r1` is minted for this solution and shared by its two triples. The second solution gives the same pattern with `cmp:Tentris` and a new node `_:r2`. The third gives `ppl:Monica rel:at _:m`, `ppl:Monica rel:id _:r3` and `_:r3 rel:belongsTo ppl:Monica`. None of the nine instantiated triples is identical to another, because the minted nodes differ, so the set union keeps all nine. The graph has four distinct blank nodes: `_:m`, carried over from the data through `?name`, and `_:r1`, `_:r2` and `_:r3`, minted by the template. Oxigraph returned exactly nine triples with four distinct blank-node labels, and its Monica line, `ppl:Monica rel:at _:bf30a224bcdb94510251d53115dae29f`, carries the data node's label. Every panel engine returned the same nine-triple graph.
