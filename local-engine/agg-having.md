# HAVING: Filtering Aggregated Groups (local-engine)

## Overview

`agg-group-count.md` showed how `GROUP BY` sorts solutions into groups and how `COUNT` turns each group into a single number. `HAVING` is the next step: it keeps or drops whole groups based on a condition, usually about an aggregate, in the same way that `FILTER` keeps or drops individual solutions. Dropping one group removes one result row, but it also discards every `WHERE` solution that group was built from. The exercise reuses the dataset from `agg-group-count/data.ttl` unchanged, copied verbatim as `agg-having/data.ttl`. It has 18 triples about five people. Bob has two `rel:worksAt` values, Alice and Monica one each, and Ben and James none. Six queries, `q1.rq` to `q6.rq`, build on it. The target is `local-engine`. The primary engine was Oxigraph 0.5.11 (`ghcr.io/oxigraph/oxigraph:0.5.11`), chosen by a fresh live lookup for three reasons: it is actively maintained and free, its `query --explain` prints the evaluation tree, and it is not the engine (Fuseki) on which the implicit-group-over-zero-matches result had been seen. Under the panel rule adopted this session, every saved query file also ran on Tentris v1.4.0, Apache Jena Fuseki 6.2.0 (built from the official Maven kit), Eclipse RDF4J 6.1.0 and QLever (image digest `dc93f8df…`), silently by default, while the one-off unbracketed variant of `q2` ran on Oxigraph alone. The panel was surfaced in the dialogue only where engines disagreed or broke the specification, which happened for `q3` and `q4` and for QLever's integer datatype.

## Where HAVING sits in the algebra

§18.2.4.2 of the SPARQL 1.1 specification translates each `HAVING(E)` as `P := Filter(E, P)`. At that point `P` already contains the grouping and the aggregation from §18.2.4.1. The SELECT expressions are only added later, in §18.2.4.4, as `Extend` operations wrapped around that `Filter`. That ordering is what the specification means when it says "expressions projected by the SELECT clause are not visible to the HAVING clause". The same §18.2.4.1 loop also rewrites every unaggregated variable in a HAVING expression as `Sample(V)`. Sample, defined in §18.5.1.8, returns an arbitrary member of the multiset it is given, and `Sample({}) = error`. Evaluation follows the same rules as FILTER, which `filter-unbound.md` established: only T keeps a group, and both F and E drop it. The grammar matters too. A `HavingCondition` is a `Constraint`, which must be either a bracketed expression, a built-in call (aggregates count as built-in calls) or a function call. `HAVING count(?x) > 1` therefore stops parsing after `count(?x)`, because `>` cannot start another condition.

## Engine panel outcomes

All five engines agreed on q1, q2, the corrected q5 and both runs of q6, apart from QLever. QLever stored the dataset's integers as `xsd:int` and returned every count as `xsd:int`, where the other four used `xsd:integer`, the datatype the specification gives COUNT. The engines disagreed on two queries. On q3, Tentris, Fuseki and QLever answered HTTP 400 with the rule that aggregates may only appear in SELECT, HAVING and ORDER BY, while Oxigraph and RDF4J answered HTTP 200 with zero rows. On q4, Oxigraph returned zero rows. Tentris rejected the query with `Non-aggregated variable ?employers is not part of the group key`. Fuseki, RDF4J and QLever returned Bob's row.

## Observable behavior

The Graph Store dump held 18 triples, matching the file. `q1.rq` (`rel:name` required, `rel:worksAt` optional, `GROUP BY ?person`, projecting `count(?employer)` and `count(*)`) returned five rows: Bob 2 and 2, Alice 1 and 1, Monica 1 and 1, Ben 0 and 1, James 0 and 1. All counts were `xsd:integer`, and Oxigraph's row order was Alice, James, Monica, Ben, Bob. `q2.rq` added `having (count(?employer) > 1)` and returned exactly one row, Bob with `"2"^^xsd:integer` for both counts. The same condition written without brackets gave HTTP 400 on Oxigraph, `error at 11:1: expected one of CEIL, LANG, RAND, SHA1, UUID, YEAR, [_]`. `q3.rq` moved the condition into a `FILTER` inside `WHERE` and returned HTTP 200 with an empty `bindings` array. `q4.rq` used the alias, `having (?employers > 1)`, and also returned zero rows. The first version of `q5.rq` projected `?person` next to `count(*)` with no `GROUP BY`, and every engine rejected it with HTTP 400. With `?person` removed, it returned one row, `"5"^^xsd:integer`, for `having (count(*) > 3)`. `q6.rq` matched the absent predicate `rel:namex`. With `> 3` it returned zero rows. With `having (count(*) = 0)` it returned one row, `"0"^^xsd:integer`.

## Internal mechanism

Oxigraph's plan for q2 was, from the outside in: `Project`, `Extend(… -> ?rows)`, `Extend(?ed9855… -> ?employers)`, `Filter((?ed9855… > 1))`, `Aggregate(?person, COUNT(?employer) -> ?ed9855…, COUNT(*) -> ?292cae…)`, `ForLoopLeftJoin`, and the two `QuadPattern`s. Solutions flow upward through this tree. Each operation sees only what the operations below it have bound. The hidden variable `?ed9855…` is the specification's temporary agg-i, and the `Filter` reads it after `Aggregate` has bound it. For q3 the plan put that same kind of `Filter` *below* the `Aggregate`. It tested a hidden variable that nothing beneath it had bound, so every comparison was E and all six left-join solutions were dropped. An explicit `GROUP BY ?person` over zero solutions forms no groups, which explains the empty result. Q4 behaves the same way on Oxigraph for a different reason, the Sample rewrite described above.

## Design rationale

Repeating the aggregate inside HAVING, as q2 does, is the only form that every engine evaluates the same way. Reusing the SELECT alias is legal SPARQL, but the specification gives it a different meaning: `Sample(?employers)` over a group in which `?employers` is never bound, which is an error. Three engines quietly substitute the SQL meaning instead, and Tentris refuses the query. Tentris is stricter than the specification, but that strictness catches what is almost always a mistake. The general tradeoff is between FILTER and HAVING. FILTER runs per solution, before any count exists. HAVING runs per group, after aggregation. A condition about a count therefore belongs in HAVING, and a condition about a single solution's values belongs in FILTER, where it also shrinks the input to grouping.

## Edge cases

The implicit group over zero matches gave one row with 0 on all five engines, which settles the question left open in `agg-group-count.md`. As that file explains, the literal SPARQL 1.1 Group formula builds no key from an empty solution sequence, while W3C errata-query-21 records the intended single group. All five engines follow the errata's intent. A HAVING condition that is true of an empty group, such as `count(*) = 0`, is the only way to make that group visible after filtering, and `> 3` cannot distinguish the two readings. Another edge case is that an aggregate inside a `WHERE` FILTER is forbidden by the grammar notes. Two of the five engines accept it anyway and silently return nothing, so a quiet empty result is not proof that a query is valid.

## Worked example

Take `q2.rq` over the five people. Matching `?person rel:name ?name` gives five solutions. The optional `rel:worksAt` extends Bob's solution twice (ID5 and Tentris) and Alice's (Tentris) and Monica's (Oracle) once each, and leaves Ben and James with `?employer` unbound, so the left join produces six solutions. Grouping by `?person` yields five groups: Bob with two solutions, and Alice, Monica, Ben and James with one each. `COUNT(?employer)` gives 2, 1, 1, 0 and 0 for these groups, because an unbound `?employer` is not counted. The HAVING `Filter` then evaluates `agg > 1` once per group. It is T only for Bob, so the four other groups and their four underlying solutions are dropped. The two `Extend`s copy Bob's hidden values into `?employers` and `?rows`, and the projection gives the single observed row, Bob with 2 and 2. Writing `?employers` in the HAVING instead, as `q4.rq` does, replaces the hidden variable with `Sample(?employers)`. Bob's two solutions bind no `?employers`, so Sample receives an empty multiset and returns an error. The comparison is E, Bob's group is dropped like all the others, and Oxigraph's result has zero rows.
