# UNION: Alternative Patterns and Variables Bound in Only One Branch (local-engine)

## Overview

Sometimes the same kind of fact is recorded with two different predicates, and a query has to find it whichever one was used. Two triple patterns in the same group cannot express that. As `bgp-first-select.md` established, a shared variable inside a group is a join, so both patterns would have to match at once. That is an AND, and the question needs an OR. SPARQL's `UNION` combines two braced groups so that a solution of either one is a solution of the whole. The exercise was a hand-written Turtle dataset of 16 triples about five people. Two predicates, `rel:worksAt` and `rel:employeeOf`, both say "a company this person is connected to", and a third predicate, `rel:age`, is recorded for only some of the people. Three queries were written: `q1.rq` uses one shared variable for the company in both branches, `q2.rq` uses a different variable in each branch, and `q3.rq` puts a required `rel:age` pattern in front of the UNION. The target is `local-engine` with Apache Jena Fuseki 6.2.0. It was built locally from the official Maven artifact `jena-fuseki-docker-6.2.0.zip`, which is needed because the project publishes no official prebuilt image, and run in memory with `--file /data/data.ttl /ds`. A fresh live lookup kept it because Jena's `arq.qparse --print=op` prints a query's algebra in the specification's own notation, which makes the new `union` operator visible next to `join`. Comparing engines was not needed, because UNION's semantics are fully specified.

## The Union operator

`optional-unbound.md` introduced solutions as mappings from variables to RDF terms, the domain of a mapping as the set of variables it binds, and compatibility as agreement on every variable in both domains. `modifier-distinct.md` introduced a result as a multiset, with card counting how often one particular solution occurs in one particular multiset. The SPARQL 1.1 specification (§18.5) defines Union with exactly these words. Its whole definition is a multiset built from the two inputs, together with a rule for how many copies of each solution it contains:

$$\mathrm{Union}(\Omega_1,\Omega_2) = \{\mu \mid \mu \in \Omega_1 \ \text{or}\ \mu \in \Omega_2\}$$

This says a solution belongs to the result if either branch produced it, and how many copies it has is stated separately:

$$\mathrm{card}[\mathrm{Union}(\Omega_1,\Omega_2)](\mu) = \mathrm{card}[\Omega_1](\mu) + \mathrm{card}[\Omega_2](\mu)$$

Read plainly, Union never compares a solution from one branch with a solution from the other. It neither checks compatibility nor merges, and it simply adds the counts, so a solution produced once by each branch appears twice. Join, defined in the same section, works the opposite way. It considers every pair of one solution from each side, keeps the compatible pairs, merges each kept pair into a single wider solution, and multiplies the counts. Neither definition says anything about order.

## Observable behavior

The Graph Store Protocol dump of the default graph contained 16 triples, which matches the file. This was confirmed again after the user renamed `rel:employerOf` to `rel:employeeOf` and the engine was restarted from scratch. `q1` returned 8 JSON bindings, each with exactly the two keys `person` and `employer`, and every value had `"type": "uri"`. Alice–Tentris, Ben–Microsoft, Monica–Oracle and Monica–Microsoft appeared once each, while Bob–Tentris and Bob–ID5 each appeared twice. James, who has neither predicate, was absent. Fuseki listed all four `worksAt` rows before all four `employeeOf` rows. `q2` also returned 8 bindings, but no two were identical. Every binding object carried `person` together with exactly one of `employer1` or `employer2`, the other key was absent, and `head.vars` still listed all three variables. `q3` returned 5 bindings: Bob with age `"30"^^xsd:integer` and Tentris twice, Bob with age 30 and ID5 twice, and Ben with age `"40"^^xsd:integer` and Microsoft once. James, Alice and Monica were absent. A first version of `q1` was rejected with `Parse error: Encountered " "." ". "" at line 1, column 48.`, because its `PREFIX` line ended with a Turtle-style dot.

## Internal mechanism

`qparse --print=op` printed `q1` as `(project (?person ?employer) (union (bgp (triple ?person rel:worksAt ?employer)) (bgp (triple ?person rel:employeeOf ?employer))))`. Each branch is its own basic graph pattern, evaluated on its own against the same graph. The `worksAt` branch yields four solutions, the `employeeOf` branch yields four, and Union adds the counts. Bob's two "same company through both predicates" solutions are therefore identical mappings that each have card 1 in their branch, so each has card 2 in the result. `q2` printed with the same shape. Here the left branch's pattern mentions only `?person` and `?employer1`, so every solution it can ever produce has exactly that domain, whatever data a person has. That is why Bob's `worksAt` rows lack `employer2` even though Bob does have `employeeOf` triples. Because the two Tentris solutions now have different domains, they are different mappings, and each has card 1.

`q3` printed as `(project (?person ?age ?employer) (join (bgp (triple ?person rel:age ?age)) (union …)))`. SPARQL has no `JOIN` keyword. The §18.2.2.6 translation joins the elements of a group, and a `union` cannot sit inside a `bgp`, so the join becomes an explicit operator. The age BGP yields Bob, Ben and James. Join pairs each of them with the eight union rows, keeping only the pairs that agree on `?person`. Bob's single age solution pairs with his four union rows, Ben's pairs with his one, and James pairs with nothing. Bob–30–Tentris has card 2, because the join multiplies card 1 on the left by card 2 on the right. The algebra fixes the result multiset, not the order in which an engine computes its pieces.

## Design rationale

UNION here expresses "a company from either source, and at least one is required". The alternative a reader might reach for, the age pattern followed by two `OPTIONAL`s, keeps every left solution: James would come back with no company, and requiring one would need an added `FILTER(bound(…))`. Join over UNION builds the requirement into the algebra itself, since a person with no union row has nothing to pair with. The cost is duplicates when both sources say the same thing, which `DISTINCT` can collapse because it compares whole rows by term (`modifier-distinct.md`). The choice of variables is a separate tradeoff. One shared variable, as in `q1`, gives one company column but loses which predicate supplied each row. Separate variables, as in `q2`, record that provenance, but the company is split across two keys, so a consumer has to check both. It also means rows from different sources never become identical, so `DISTINCT` could no longer merge them.

## Edge cases

"Unbound" now has two different causes, and the JSON output looks the same for both. In `optional-unbound.md`, Ben's `?employer` was unbound because, for that particular left solution, the data held no compatible match. It was decided by the data, row by row. In `q2`, `?employer2` is unbound in every left-branch row because that branch's pattern never mentions it. It is decided by the query's shape. In both cases the key is simply absent from the binding object. Fuseki's left-then-right row order happened to look like concatenation, but nothing in Union's definition guarantees it, and only `ORDER BY` would make an order part of the answer. Two `OPTIONAL`s sharing one company variable, where the second must be compatible with whatever the first bound, were raised as a contrast but not run.

## Worked example

Take `q3` over `data.ttl`. The left input is the age pattern on its own, which matches three triples and gives three mappings: Bob to `"30"^^xsd:integer`, Ben to `"40"^^xsd:integer`, and James to `"16"^^xsd:integer`, each pairing `?person` with `?age`. The right input is the union. Its `worksAt` branch matches Alice–Tentris, Bob–Tentris, Bob–ID5 and Monica–Oracle, and its `employeeOf` branch matches Bob–Tentris, Bob–ID5, Monica–Microsoft and Ben–Microsoft. Union adds these without comparing them, so the right input holds eight rows, with Bob–Tentris and Bob–ID5 each at card 2.

The join now pairs left with right on the only shared variable, `?person`. Bob's single age mapping agrees with his four union rows, and merging each pair gives Bob–30–Tentris and Bob–30–ID5, each at card 1 times 2, which is 2. Ben's mapping agrees with exactly one row, giving Ben–40–Microsoft at card 1. James's mapping agrees with no union row, because neither branch matched him, so he contributes nothing. Alice and Monica have union rows but no age mapping, so they are dropped too. That totals five rows. Compared as a multiset, since no `ORDER BY` was given, they matched Fuseki's five bindings exactly, and both ages kept their `xsd:integer` datatype.
