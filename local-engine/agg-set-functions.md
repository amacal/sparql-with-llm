# Aggregates Beyond COUNT: SUM, AVG, MIN, MAX, GROUP_CONCAT and SAMPLE (local-engine)

## Overview

`agg-group-count.md` established how `GROUP BY` partitions solutions and how COUNT reduces each group to a number. This exercise covers the other six SPARQL 1.1 set functions, and the new question is about values rather than counting. What datatype does a sum or an average carry? What happens when one value in a group is not a number, or is missing? Where do blank nodes sort when MIN and MAX compare arbitrary terms? Which parts of a concatenation or a sample does the specification leave open? The dataset `agg-set-functions/data.ttl` holds 18 triples about six people. Bob (30), James (16) and John (25) have `xsd:integer` ages, Ben has `40.0` (`xsd:decimal`), Monica's age is the blank node `_:unknown`, and Alice has no age. Everyone except James has a `rel:worksAt` company: Ben works at IBM and the other four at Tentris. Nine queries, `q1.rq` to `q9.rq`, each isolate one case, mostly with a FILTER over named people and no `GROUP BY`. The target is `local-engine`. The primary engine was Apache Jena Fuseki 6.2.0, built from the official `jena-fuseki-docker-6.2.0` kit. A fresh live lookup chose it again because `arq.qparse --print=op` prints the Group/Aggregation/Extend algebra in the specification's own shape. A silent panel ran every query: Oxigraph 0.5.13, Eclipse RDF4J 6.1.0, QLever, Virtuoso Open Source 7.2.17, Tentris 1.5.0 and, new to the panel, MillenniumDB built from its repository's Dockerfile. Every engine stored all 18 triples.

## Set functions over the multiset M

Each set function receives the same input, which `agg-group-count.md` derived. M(Ω) holds one `ListEval` result per solution in the group, and an unbound argument evaluates to `(error)`. Flatten unwraps the one-element lists. What differs from one function to the next is how it treats an error element and what it returns for an empty input. Count removes errors before taking the cardinality. Sum (§18.5.1.3) is a right fold over `op:numeric-add` with no removal step, and it returns `"0"^^xsd:integer` on empty input. Avg is Sum divided by Count, and it returns `"0"^^xsd:integer` when Count is 0. Min and Max order the values "as per the ORDER BY ASC/DESC clause", and both are an error on empty input. GroupConcat joins the values in an unspecified order with a default separator of U+0020, and it returns `""` on empty input. Sample returns any member of Flatten(M), is "not required to be deterministic", and is an error on empty input.

Numeric results follow F&O §6.2. Each operator works on two operands of the same type. When the types differ, the operand lower on the ladder integer → decimal → float → double is promoted to match the other. The one exception is `op:numeric-divide`, which returns `xs:decimal` for two integers. Turtle §2.5.2 decides which rung a bare number starts on: no decimal point gives an integer, a decimal point gives a decimal, and only an `e`/`E` exponent gives a double.

## Observable behavior

`q1` summed Bob, James and John and returned one row, `"71"^^xsd:integer`. Its first version, `select sum(?age)` with no parentheses and no `AS`, broke grammar rule [9]. Fuseki still answered it with a variable named `.1` and Virtuoso with `callret-0`, while the other five engines returned HTTP 400. `q2` summed Ben and John to `"65.0"^^xsd:decimal`. `q3` averaged Bob, James and John, and every engine returned `xsd:decimal` with a different number of digits, from Fuseki's `23.666666666666666666666667` to QLever's `23.66666666667`. `q4` summed Bob and Monica and returned one row whose binding object was empty, `{ }`, on all seven engines. `q5` put the age inside OPTIONAL for Bob and Alice. Every engine counted 1. Fuseki, Oxigraph, QLever, Tentris and MillenniumDB left the sum unbound, while RDF4J and Virtuoso returned 30. `q6` gave MIN `_:bnode` and MAX `40.0` for Monica, Bob and Ben. `q7` concatenated three names with `.` in three different orders across the panel, and returned "Monica" or "Ben" as the sample. `q8` matched nobody (`ppl:Adrian`) and returned one row: count 0, sum 0, avg `"0"^^xsd:integer`, min and max unbound, concatenation `""`, sample unbound. Virtuoso differed there by leaving sum and avg unbound. `q9` grouped by `?workplace` with `having (sum(?age) >= 0)` and returned only IBM, `40.0`. On that query Virtuoso failed the whole request with HTTP 500 and `SR087: Non numeric argument(s) to arithmetic operation '+'`.

## Internal mechanism

Fuseki printed `q2` as `(project (?totalAge) (extend ((?totalAge ?.0)) (group () ((?.0 (sum ?age))) (filter … (bgp …)))))`. The empty key list means every solution receives the key `()`, so there is exactly one group. The aggregate is computed once, into the hidden variable `?.0`, and the alias is attached afterwards by `extend`, following §18.2.4.1. This is why one aggregate can serve SELECT, HAVING and ORDER BY without being evaluated three times. When the aggregate is an error, Extend's second case (`Extend(μ, var, expr) = μ` if `expr(μ)` is an error) returns the solution unchanged. The row survives with the variable absent, which is exactly the `{ }` of `q4`. In `q9` the HAVING became `(filter (>= ?.0 0) …)`, applied to the group's hidden value. For Tentris, `error >= 0` is itself an error, an error is not true, and so the filter drops the group.

## Design rationale

A query that should give one answer on every engine must not let SUM see an unbound or non-numeric value, because `q5` showed the engines split on that point. The simplest guard is a WHERE-clause filter, either `FILTER(BOUND(?age))` or the stricter `FILTER(?age + 0 = ?age)`, which uses an error to reject non-numbers as well. The price is that the filtered solutions disappear completely: `COUNT(*)` in `q5` would fall from 2 to 1, and nothing would show that Alice existed. Relying on HAVING to discard groups through an error, as `q9` does, is more fragile still. Changing Monica's age to `1.5e1` would make Tentris reappear with `70` as `xsd:double`, whereas a WHERE filter returns Tentris as `55` (integer) before that change and as `70` (double) after it. The empty-input rules follow from identity elements. 0 leaves a sum unchanged and `""` leaves a concatenation unchanged, so both remain correct when an empty group is combined with others. No term sorts above every other term, so MIN over nothing has no answer and is an error.

## Edge cases

Lexical forms are the engine's choice: Oxigraph and Virtuoso stored Ben's age as `"40"` and returned `"65"`, which are different terms from `"40.0"` and `"65.0"` with the same values. The rounding of non-terminating decimals is also left to the implementation. QLever's `xsd:int` results (`q1`, `q5`, `q8`) differ from the `xsd:integer` that the F&O table gives integer addition. A tie between `40` and `40.0` under MAX would be undetermined by the specification, though this was reasoned through and not run.

## Worked example

Take `q9` over the original data. The required patterns `?person rel:worksAt ?workplace` and `?person rel:age ?age` match Bob, Monica and John at Tentris and Ben at IBM. Alice has no age and James has no company, so neither produces a solution. Grouping by `?workplace` gives two groups. For Tentris, M after Flatten is `{"30"^^xsd:integer, _:unknown, "25"^^xsd:integer}`. Sum folds `op:numeric-add` over these values, and the moment it reaches the blank node it raises a type error, so the whole Sum is an error. For IBM, M is `{"40.0"^^xsd:decimal}`, and `op:numeric-add(40.0, 0)` promotes the integer 0 and returns `40.0` as a decimal. Fuseki's printed algebra places Extend directly above the group, so Extend first copies each group's hidden `?.0` into `?totalAge`, leaving it unbound for Tentris and binding `40.0` for IBM. The HAVING filter above it then tests the hidden `?.0 >= 0` once per group. For Tentris the result is an error and the group is dropped. For IBM, `40.0 >= 0` is true and the group is kept, and the projection gives the single observed row, IBM with `"40.0"^^xsd:decimal`. Six engines returned exactly that row, written `"40"` by Oxigraph, while Virtuoso failed the request.
