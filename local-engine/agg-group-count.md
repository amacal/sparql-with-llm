# GROUP BY and COUNT: Aggregating Solutions into Groups (local-engine)

## Overview

Every query in the earlier exercises returned one row per solution, but many real questions ask about a whole collection of solutions at once, such as how many employers each person has. SPARQL answers these with aggregates. The solutions of the `WHERE` clause are first sorted into buckets called groups, each group is identified by a group key (the value of the `GROUP BY` expression), and an aggregate such as `COUNT` then turns each group into a single value. The exercise is a hand-written Turtle dataset of 18 triples about five people (Bob has two `rel:worksAt` and two `rel:employeeOf` values, Alice and Monica one `rel:worksAt` each, Monica's `rel:employeeOf` is a blank node, and Ben and James have no `rel:worksAt`), together with eleven queries `q1.rq` to `q11.rq`. The target is `local-engine` with Apache Jena Fuseki 6.2.0, built locally from the official Maven artifact `jena-fuseki-docker-6.2.0.zip` and run in memory with `--file /data/data.ttl /ds`. A fresh live lookup chose it because Jena's `arq.qparse --print=op` prints the aggregation algebra (`group`, `extend`, `project`) in the specification's own terms.

## Group, Aggregation and Count

`modifier-distinct.md` defined card as the number of occurrences of one identical solution in a multiset, and `union-alternatives.md` showed that a join keeps every compatible pair and therefore multiplies cardinalities. Grouping builds on both. The SPARQL 1.1 specification (§18.5.1) defines Group as a set of entries, one per solution it iterates over. Each entry maps a key, produced by evaluating the `GROUP BY` list against that solution, to all solutions sharing that key:

$$\mathrm{Group}(exprlist,\Omega) = \{\, \mathrm{ListEval}(exprlist,\mu) \rightarrow \{\mu' \mid \mu' \in \Omega,\ \mathrm{ListEval}(exprlist,\mu) = \mathrm{ListEval}(exprlist,\mu')\} \mid \mu \in \Omega \,\}$$

The formula has two consequences used throughout this exercise. A key only exists if some solution produced it, and ListEval of an unbound variable is defined as `(error)`, so an unbound grouping variable produces a key too. Aggregation then applies a set function to the multiset M(Ω), which holds one evaluated argument list per solution in the group. Count is defined by flattening M and discarding errors before taking the size:

$$\mathrm{Count}(M) = \mathrm{card}[\, \mathrm{Flatten}(M) \setminus \text{errors} \,]$$

In plain terms, `COUNT(?x)` counts how many solutions in the group have `?x` bound. `COUNT(*)` is a special case defined as card[Ω], the number of solutions in the group, so it never evaluates anything. With `DISTINCT`, Distinct is applied to M(Ω) before counting.

## Observable behavior

Every count fetched as JSON came back as a literal with datatype `xsd:integer`, and no query had `ORDER BY`, so row order was never part of what was checked. The Graph Store Protocol dump contained 18 triples, which matches the file, with Monica's `[]` stored under an engine-chosen blank node label. `q1` (required `rel:worksAt`, `COUNT(?employer)`) returned three rows: Alice 1, Monica 1 and Bob 2. `q2` added a required `rel:name` and made `rel:worksAt` optional, and it returned five rows, the same three plus Ben 0 and James 0. `q3` is `q2` with `COUNT(*)` and gave Ben 1 and James 1 with everyone else unchanged (this run used CSV, so the datatype was not visible there). `q4` reused one `?employer` variable in both the `rel:worksAt` and `rel:employeeOf` patterns, which made the company a join condition, and it returned only Bob 2. `q5` used separate variables and gave Bob 4 and 4 and Monica 1 and 1, with the blank node counted like any other term. `q6` put `DISTINCT` inside both aggregates and gave Bob 2 and 2. `q7` had no `GROUP BY` and returned one row, 4. `q8` used a predicate absent from the data (`rel:worksAt2`) and still returned exactly one row, 0, while `q9`, the same with `GROUP BY ?person`, returned zero rows with both variables still listed in `head.vars`. `q10` grouped by `?employer` and returned ID5 1, Tentris 2, Oracle 1, and a fourth row whose binding object had no `employer` key and whose count was 2. `q11` projected the non-grouped `?name` and Fuseki rejected it with HTTP 400 and `Parse error: Non-group key variable in SELECT: ?name`.

## Internal mechanism

For `q2` the printed algebra was `(project (?person ?employers) (extend ((?employers ?.0)) (group (?person) ((?.0 (count ?employer))) (leftjoin …))))`. Reading inside out, the left join produces six solutions. `group` maps each `?person` key to its solutions and computes the count into the temporary variable `?.0`, which is the specification's agg-i from §18.2.4.1. `extend` exists because of `AS`, and copies `?.0` into `?employers`, and `project` drops everything except `?person` and `?employers`. For `q7` the algebra shows `group ()` with `(count)`, which is Jena's form of the implicit single group (the specification's constant key `(1)`) and of `COUNT(*)`. In `q5`, Bob's group holds the four solutions of the 2-by-2 join, so M(Ω) for `COUNT(?employer1)` is `{(ID5), (ID5), (Tentris), (Tentris)}` and Count returns 4. `q6` deduplicates that multiset to `{(ID5), (Tentris)}` before counting.

## Design rationale

The question "how many employers does each person have, including people with none" needs three choices together. A pattern that every person has (`rel:name`) keeps people in the solutions. `OPTIONAL` around `rel:worksAt` stops a missing employer from removing the person, and `COUNT(?employer)` rather than `COUNT(*)` makes that person's single solution count as 0 instead of 1. A required `rel:worksAt` (as in `q1`) can never report 0, because a person with no match never reaches the grouping step. `COUNT(DISTINCT …)` after a join of two multi-valued properties gives the right numbers here, but it repairs an inflation the query itself created, and it would undercount wherever the counted variable can legitimately repeat across genuinely different solutions, for instance one value reached through two different properties or paths. Counting each property in its own subquery and joining the per-person counts afterwards avoids the inflation; that was named during the session and left for later. Projecting a non-grouped variable is forbidden (§11.4) because a group such as Tentris holds both "Alice" and "Bob" as `?name`, so a single value per row is undefined unless an aggregate, `SAMPLE` if any value will do, says how to pick one.

## Edge cases

The implicit group over zero matches is a genuine defect in the 1.1 text. Read literally, Group iterates over the solutions in Ω, so an empty Ω produces no key, no group and zero rows. W3C's errata entry query-21, with Andy Seaborne's linked note, records this and states the intent of one row with Count({}) = 0, which is what Fuseki returned for `q8`. With an explicit `GROUP BY` (`q9`) there really is no group, Count is never called, and zero rows is the intended answer. This was observed on one engine only. The second edge case is grouping by a sometimes-unbound variable. Ben's and James's keys are both `(error)`, equal keys share a group, and the specification removes error values "at projection time", which removes the pair but keeps the row.

## Worked example

Take `q10` over the five people. The pattern `?person rel:name ?name` matches all five, and the optional `rel:worksAt` extends Bob twice (ID5 and Tentris), Alice once (Tentris) and Monica once (Oracle), while Ben and James keep their single solutions with `?employer` unbound. That gives six solutions. Grouping by `?employer` evaluates `?employer` in each one, so Bob-ID5 gets key `(ID5)`, Bob-Tentris and Alice get `(Tentris)`, Monica gets `(Oracle)`, and Ben and James both get `(error)`. Four keys therefore produce four groups, holding one, two, one and two solutions respectively. `COUNT(*)` takes card[Ω] of each group and so yields 1, 2, 1 and 2. In the projection the `(error)` key cannot become a binding, so the JSON result is exactly the four rows Fuseki returned, ID5 1, Tentris 2, Oracle 1, and a row containing only `"rows": "2"^^xsd:integer` with no `employer` key, while `employer` remains listed in `head.vars`. Had the query used `COUNT(?employer)` instead, that last group's M(Ω) would be `{(error), (error)}`, which is empty once errors are removed, and the row would read 0.
