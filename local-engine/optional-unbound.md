# Optional Pattern with an Unbound Variable (local-engine)

## Overview

A basic graph pattern only returns a solution when every triple pattern matches (`bgp-first-select.md`). That is too strict for a question like "every person with their age, and their employer if the graph records one". RDF has no null term: a subject either has a triple with a given predicate or it does not. SPARQL's `OPTIONAL` keeps every solution of the pattern to its left, extends it with extra bindings where the optional pattern matches, and otherwise keeps it unchanged with the optional variable left out. The exercise was a hand-written eight-triple Turtle dataset about four people and six queries, `r1.rq` to `r6.rq`, all with full IRIs. The target is `local-engine` with Oxigraph 0.5.11 (image `ghcr.io/oxigraph/oxigraph:0.5.11`), in memory, queried over the SPARQL 1.1 Protocol with JSON results. A fresh live lookup confirmed it is actively maintained, and it was kept deliberately so that OPTIONAL is the only change compared with the previous session's query plan.

## Unbound means "not in the domain"

`bgp-first-select.md` established that a solution is a mapping from variables to RDF terms, and that a variable the mapping assigns is called bound. The new idea here is the reverse case. A mapping only lists the variables it actually has values for. That set is called its domain, and nothing requires the domain to contain every variable the query mentions. A variable that is not in the domain is unbound. Unbound is not a special value standing in the variable's place. It is the absence of a pair. A person with no employer triple gets a two-pair mapping, not a third pair pointing at a null.

The SPARQL 1.1 spec (§18) builds both joins out of one notion, compatibility. Two mappings are compatible if, for every variable in both of their domains, they map it to the same RDF term. Only the shared variables are checked. A variable that only one side binds is never compared, so it can never be the reason two mappings fail to combine. Compatible mappings can be merged into their union. With that in place, the left join behind `OPTIONAL` can be written down. Spelled out in full, it is the union of two sets, built from the left side's solutions and the optional pattern's solutions, with the filter expression fixed to the constant `true` that a plain `OPTIONAL` always uses:

$$\mathrm{LeftJoin}(\Omega_1,\Omega_2,\mathrm{true}) = \{\mathrm{merge}(\mu_1,\mu_2) \mid \mu_1\in\Omega_1,\ \mu_2\in\Omega_2,\ \mu_1,\mu_2\ \text{compatible}\} \ \cup\ \{\mu_1\in\Omega_1 \mid \text{no}\ \mu_2\in\Omega_2\ \text{is compatible with}\ \mu_1\}$$

The first set is an ordinary join. The second set takes back every left solution that found no partner and keeps it unchanged. Each left solution therefore comes out either once, unchanged, or once per compatible right-hand match. That is why adding an `OPTIONAL` can never make a result smaller.

## Observable behavior

The dump of the in-memory store after loading `data.ttl` contained eight triples. Bob is aged 46 and works at ID5 and at Tentris, Alice is aged 20 and works at Tentris, Ben is aged 21 and has no `worksAt` triple, and James is aged 16 and works at a blank node, which the store labelled `e806fdb4...`. Every age was stored as an `xsd:integer`. `r1.rq` required both patterns and returned four solutions: James with the blank node, Alice with Tentris, and Bob twice. Ben was absent. `r4.rq`, with `aged` required first and `worksAt` inside `optional` after it, returned five solutions. Ben's JSON binding object contained only the keys `"person"` and `"age"`, while `head.vars` still listed `"employer"`. That is exactly what the SPARQL 1.1 JSON results spec requires: "A variable does not appear in an array element if it is not bound in that particular query solution." `r5.rq` required a predicate no subject has and returned `{"head":{"vars":["person","age","years"]},"results":{"bindings":[]}}`, which shows that `head.vars` comes from the query, not the data. `r6.rq` made that pattern optional and returned all four people once, with no `"years"` key anywhere. `r2.rq` (optional `aged`) and `r3.rq` (the `optional` block written first) both returned `r1`'s four solutions.

## Internal mechanism

Oxigraph's `query --explain --stats` was run for `r4` against a separate on-disk store, loaded once. Its plan showed `Project(?person, ?age, ?employer)` with 5 results, over `ForLoopLeftJoin(expression = "true"^^xsd:boolean)` with 5 results, over two `QuadPattern` nodes. The `aged` node produced 4 results and the `worksAt` node 4. The `expression = true` in the join node is the spec's filter argument appearing directly in the plan. "ForLoop" means the right-hand pattern is evaluated once per left-hand solution with `?person` already substituted. The four runs returned 1 for James, 0 for Ben, 1 for Alice and 2 for Bob, which adds up to the reported 4. Ben's run returning zero is how the engine knows his solution belongs in the second set. The join node's 5 is the four merged solutions plus Ben unchanged, where the previous session's `Lateral` join would have dropped him.

`r3` shows that the left side of an `OPTIONAL` is whatever is written before it in the group. The §6.1 text states that `{ OPTIONAL { pattern } }` is equivalent to `{ { } OPTIONAL { pattern } }`. An empty group produces exactly one solution, the empty mapping, much like Oracle's one-row `DUAL` table. Sharing no variables, it is compatible with every `worksAt` match, so the left join yields the four `worksAt` solutions. The `aged` pattern is then joined to them as a required pattern. A required join has no "keep the unmatched" set, and Ben's `aged` mapping disagrees with all four on `?person`, so it is dropped.

## Design rationale

`r4` puts the pattern every result must satisfy (having an age) first and the pattern that may be missing (an employer) after `optional`, because the order decides what the left side is. Reversing them, as `r3` did, makes the employer the defining pattern and loses everyone without one. Using `OPTIONAL` instead of a required pattern expresses "include it if present", which `r5` versus `r6` shows sharply: the same two triple patterns give zero rows or four depending on one keyword. The alternative of sending two required queries and merging them on the client would happen to work here, because the join key `?person` is always an IRI, and IRIs mean the same thing everywhere. It would not be reliable if the join key were a blank node. §2.4 scopes blank node labels to a single result set, so a label in one response has no guaranteed relation to the same label in another. The left join done inside the engine compares the actual nodes rather than their printed labels.

## Edge cases

James's blank-node employer came back as `"type": "bnode"` labelled `e806fdb4...`, matching the serve store's dump. The separately loaded explain store labelled it `d611b4f6...`, because each load mints a fresh node, and its TSV output showed Ben's unbound employer as an empty field. Deferred were an optional group of two triple patterns, which contributes only if the whole group matches (§6.1), two independent OPTIONALs (§6.3), and how an unbound variable behaves inside a `FILTER` comparison.

## Worked example

Take `r4` over `data.ttl`. The required `aged` pattern matches four triples, so the left-hand set holds four mappings: Bob to 46, Alice to 20, Ben to 21, and James to 16, each pairing `?person` with `?age`. The optional `worksAt` pattern on its own matches four triples, so the right-hand set holds Bob with ID5, Bob with Tentris, Alice with Tentris, and James with the blank node, each pairing `?person` with `?employer`. Only `?person` appears on both sides, so compatibility means agreeing on the person. Bob's left mapping is compatible with both of Bob's right mappings, giving two merged solutions with age 46, while Alice and James are each compatible with exactly one, giving Alice, 20, Tentris and James, 16, the blank node. That makes four merged solutions, all in the first set.

Ben's left mapping is checked against all four right mappings, and each one binds `?person` to someone other than Ben. Ben is compatible with none of them, so his mapping goes into the second set and is kept as the two-pair mapping of Ben and 21. The total is four plus one, which is five solutions. The engine returned exactly these five, in the order James, Ben, Alice, Bob with Tentris, Bob with ID5. They were compared as a multiset, since no `ORDER BY` was given. Ben's binding object had no `"employer"` key at all.
