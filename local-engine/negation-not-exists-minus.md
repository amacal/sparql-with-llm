# Negation: FILTER NOT EXISTS Versus MINUS (local-engine)

## Overview

SPARQL 1.1 has two keywords for "which solutions have no matching X": `FILTER NOT EXISTS { P }` and `MINUS { P }`. They agree on the everyday case, which invites treating them as synonyms. Nine hand-written queries over a 19-triple people dataset compare them, with the SPARQL 1.0 idiom `OPTIONAL` plus `FILTER(!bound(...))`, and pin down where they diverge. The target is `local-engine`. The primary engine was Apache Jena Fuseki 6.2.0, built from Apache's official `jena-fuseki-docker` kit and loaded in memory from `data.ttl`, chosen because Jena's `qparse --print=op` prints the algebra, which is exactly where the two forms differ. A silent panel of Oxigraph 0.5.11, Eclipse RDF4J 6.1.0, QLever, Tentris v1.4.0 and Virtuoso Open Source 7.2.17 ran every query alongside it.

## How the two negations are defined

`MINUS` reuses machinery that `filter-optional-scope.md` already derived for `Diff`, the operator behind `LeftJoin`: a left mapping survives only if every right mapping is harmless to it. Compatibility is the same notion as in `optional-unbound.md`, where two mappings are compatible when no variable bound in both has different values. The spec's `Minus(Ω1, Ω2)` keeps a left mapping μ when every right mapping μ′ is either not compatible with μ or has a domain disjoint from μ's. That second escape route replaces `Diff`'s expression route, and it exists because two mappings sharing no variables are always compatible. Without it, any non-empty right side would remove every left row. Both sides of `MINUS` are evaluated independently, so the right side never sees any of the left side's values.

`FILTER NOT EXISTS` is not a binary operator at all. It is a filter expression evaluated once per outer solution μ. The spec's §18.6 defines `substitute(P, μ)` as the pattern obtained by replacing each variable in dom(μ) with its value from μ, and `exists(P)` as true exactly when that substituted pattern has at least one solution in the dataset. A variable that μ does not bind stays a free variable in the substituted pattern and can match anything. The test adds no bindings, so a variable used only inside the braces never reaches the result. Because it is only a test, it also never multiplies rows, however many matches the inner pattern finds.

## Engine panel outcomes

Fuseki, Oxigraph, RDF4J and Tentris matched the specification on every query. Virtuoso 7.2.17 departed from it four times: zero rows on q4 where nothing may be removed, Bob removed on q6 because its `MINUS` side saw the outer `?name`, and Alice kept on q8 and q9 although her free `?employer` should have matched. So Virtuoso appears to give `MINUS` the outer-variable visibility of `NOT EXISTS`. Its Alice result fits an unbound variable compared as a SQL `NULL`, but that is an unverified hypothesis. QLever departed once, keeping Bob on q7: its inner `FILTER` did not see the substituted `?name`, the mirror image of Virtuoso's q6. QLever again stored integers as `xsd:int`.

## Observable behavior

The four paired queries give the clearest picture. With the right side `?person rel:employeeOf ?employer`, q3 (`MINUS`) and q2 (`NOT EXISTS`) both returned 3 rows: Alice, James and `cmp:ID5`. q1, the `OPTIONAL` plus `!bound` version, returned the same three rows. With `?p1 rel:employeeOf ?employer`, which shares no variable with the left side, q4 (`MINUS`) returned all 6 named subjects and q5 (`NOT EXISTS`) returned 0. With `?person rel:employeeOf ?employer` plus an inner `FILTER(?name = "Bob")`, q6 (`MINUS`) returned 6 rows and q7 (`NOT EXISTS`) returned 5, without Bob. In q9 (`MINUS`) and q8 (`NOT EXISTS`), an outer `OPTIONAL` binds `?employer` from `rel:employeeOf` and the inner pattern is `?person rel:worksAt ?employer`. Both returned the same 4 rows: Ben with `cmp:Microsoft`, Monica with her blank node, and James and `cmp:ID5` with `?employer` unbound, shown as an empty TSV cell and as a missing key in JSON. No query used `ORDER BY`, so row order carried no meaning.

## Internal mechanism

`qparse --print=op` turned q2 into `(filter (notexists (bgp (triple ?person rel:employeeOf ?employer))) (bgp (triple ?person rel:name ?name)))` and q3 into `(minus (bgp (triple ?person rel:name ?name)) (bgp (triple ?person rel:employeeOf ?employer)))`. The inner pattern is identical in both, but it sits in different places. Under `notexists` it is evaluated once per outer row after substitution. As the second operand of `minus` it is evaluated once, on its own. q6's algebra put `(filter (= ?name "Bob") ...)` inside the right operand of `minus`, over a pattern that never binds `?name`. The comparison therefore raises an error for every right row, the right side is empty, and nothing is removed. q7's algebra put the same filter inside `notexists`, where substitution has already replaced `?name` with the outer value.

The pattern behind all four pairs follows from this. The two forms agree whenever every outer variable the right side depends on is shared with it through a triple pattern, because then compatibility and substitution test the same thing. They differ when nothing is shared (q4/q5), or when the link to the outer row exists only inside a `FILTER` (q6/q7).

## Design rationale

`NOT EXISTS` is the right tool when the negated condition depends on outer values, as in q7. `MINUS` is a self-contained set difference keyed on shared variables, and its disjoint-domain rule makes it the safer of the two when a right side accidentally shares nothing: a variable typo then removes nothing (q4) instead of everything (q5). The `OPTIONAL` plus `!bound` idiom predates both and states the intent only indirectly. The session also raised a fair objection: q6 is legal although `?name` can never be bound where its `FILTER` sits, so a refactoring typo shows up as silently different results. Requiring filter variables to be *definitely* bound would break q1's deliberate `!bound`, while requiring them to be *possibly* bound would catch q6. The spec adopts neither and lets the case evaluate as an error, leaving typo detection to tooling. Two of six engines got the distinction wrong in opposite directions, the practical argument for checking negation on more than one engine.

## Edge cases

Monica's `rel:employeeOf` value is a blank node, and q1 still excluded her, because `bound()` asks only whether a variable has a value, not what kind of term it is. In the first q8 run, which used `rel:employeeOf` inside, the blank node was substituted into the inner pattern and matched Monica's stored triple, so every engine removed her. A variable-free right side was only reasoned through: its single solution has an empty domain, disjoint from every left domain, so `MINUS` would remove nothing while `NOT EXISTS` would remove every row whenever the fixed triple exists. The `substitute` errata (errata-query-8 and errata-query-10) were not probed.

## Worked example

The dataset contains these triples, among others: `ppl:Alice rel:name "Alice"` and `ppl:Alice rel:worksAt cmp:Tentris`; `ppl:Bob rel:employeeOf cmp:ID5`, `ppl:Bob rel:employeeOf cmp:Tentris`, `ppl:Bob rel:worksAt cmp:ID5` and `ppl:Bob rel:worksAt cmp:Tentris`; `ppl:Ben rel:employeeOf cmp:Microsoft`; and `ppl:Monica rel:employeeOf _:b` and `ppl:Monica rel:worksAt cmp:Oracle`. James and `cmp:ID5` have only names among the relevant predicates. q8 asks for each named `?person`, `OPTIONAL { ?person rel:employeeOf ?employer }`, then `FILTER NOT EXISTS { ?person rel:worksAt ?employer }`, projecting `?person ?employer`. After the `OPTIONAL` there are seven outer rows: Bob twice, once with `cmp:ID5` and once with `cmp:Tentris`; Ben with `cmp:Microsoft`; Monica with `_:b`; and Alice, James and `cmp:ID5`, each with `?employer` unbound.

Substitution decides each row. Bob's two rows become `ppl:Bob rel:worksAt cmp:ID5` and `ppl:Bob rel:worksAt cmp:Tentris`. Both triples exist, so both rows are removed. Ben's row becomes `ppl:Ben rel:worksAt cmp:Microsoft`, which does not exist, so it is kept. Monica's becomes `ppl:Monica rel:worksAt _:b`, which also does not exist, because her `worksAt` value is `cmp:Oracle`, so she is kept. Alice's `?employer` is not in her mapping's domain, so it stays free. `ppl:Alice rel:worksAt ?employer` matches Tentris, and Alice is removed even though she has no employer to compare against. James and `cmp:ID5` stay free too, but match nothing, so they are kept. The expected result is 4 rows, and Fuseki returned exactly those 4. q9 replaces the filter with `MINUS`, and its trace reaches the same 4 rows by a different route. Alice's left domain {?person, ?name} shares `?person` with the right row {?person → ppl:Alice, ?employer → cmp:Tentris}, the two are compatible, and neither escape route applies, so Alice is removed. Monica's left `_:b` conflicts with the right side's `cmp:Oracle`, so she is incompatible and kept.
