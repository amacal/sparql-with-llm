# Property Paths: Transitive Traversal with + and * (local-engine)

## Overview

Up to now every triple pattern in this repo matched exactly one arrow of the graph. If you draw each triple as an arrow from its subject to its object, labelled with its predicate, a *path* is a chain of arrows followed head to tail, its *length* is the number of arrows, and a node Y is *reachable* from X when some path leads from X to Y. A property path lets one triple pattern say "follow this kind of arrow some number of times". This exercise compared the fixed-length sequence path `/` with the arbitrary-length forms `+` (one or more steps) and `*` (zero or more steps). The question was whether a node reached by several routes appears once per route or once. The dataset is a hand-written Turtle file of people linked by `rel:reportsTo`. It went through three versions during the session, described below, and six queries `q1.rq` to `q6.rq` each project a single `?boss` from a fixed start person. The target is `local-engine` with Apache Jena Fuseki 6.2.0, built locally from the official Maven artifact `jena-fuseki-docker-6.2.0.zip` (SHA-1 verified) and run in memory with `--file /data/data.ttl /ds`. This is the third session on Fuseki, kept deliberately by the fresh lookup because its bundled `arq.qparse` prints algebra, showing which path forms become ordinary joins.

## Two kinds of path in the specification

The §9.1 table of the SPARQL 1.1 Query Recommendation defines `elt1 / elt2` as "A sequence path of elt1 followed by elt2", and `elt+` and `elt*` as paths that connect "the subject and object of the path by one or more" (or "zero or more") "matches of elt". A path expression occupies only the predicate slot of a triple pattern. In `ppl:Ben rel:reportsTo/rel:reportsTo ?boss` the subject is `ppl:Ben`, the object is `?boss`, and the two path elements are just `rel:reportsTo` each time, so the expression describes exactly two steps whatever the data holds. §18.2.2.4 then splits the path forms into two families. A sequence is rewritten into triple patterns joined through a fresh variable (`?s :p/:q ?o` becomes `?s :p ?_V . ?_V :q ?o`). The Recommendation's own table row prints this as `X P ?V . ?V Q P`, which is a typo for `?V Q Y`, as its worked example shows. Every other form, including `+` and `*`, is wrapped in a general `Path(...)` operator. §9.3 warns that the rewritten forms "can lead to duplicates" because the fresh variable is hidden by projection. §9.4 says the opposite about `+` and `*`: "Such connectivity matching does not introduce duplicates (it does not incorporate any count of the number of ways the connection can be made)".

## Observable behavior

The data had three versions. Version A held 14 triples, with the `rel:reportsTo` arrows Alice→Bob, Ben→Alice, Monica→Bob and Monica→Alice, plus names and ages for five people, including James, who has no `rel:reportsTo` triple at all. Version B added Ben→Monica (15 triples, confirmed by a Graph Store Protocol dump). Version C added Bob→Ben, which closes a cycle (16 triples). On version A, `q1.rq` (`ppl:Monica rel:reportsTo+ ?boss`) returned two bindings, Alice and Bob, even though Monica reaches Bob both directly and through Alice. On version B, `q2.rq` (`ppl:Ben rel:reportsTo/rel:reportsTo ?boss`) returned three bindings, Bob, Alice, Bob, in that order with the two Bob rows not adjacent. `q3.rq` (`ppl:Ben rel:reportsTo+ ?boss`) returned Alice, Bob and Monica once each. `q4.rq` (`ppl:Ben rel:reportsTo* ?boss`) returned Ben, Alice, Bob and Monica. `q5.rq` (`ppl:James rel:reportsTo* ?boss`) returned the single binding James, and `q6.rq` (`ppl:Nobody rel:reportsTo* ?boss`) returned the single binding `http://example.com/people/Nobody`, an IRI that appears nowhere in the file. On version C, the unchanged `q3.rq` returned four bindings, Alice, Bob, Ben and Monica, and terminated normally. Every value had `"type": "uri"`.

## Internal mechanism

`qparse --print=op` showed Jena's algebra straight after parsing. For `q2` it was `(project (?boss) (path ppl:Ben (seq rel:reportsTo rel:reportsTo) ?boss))`, and for `q3` it was `(project (?boss) (path ppl:Ben (path+ rel:reportsTo) ?boss))`. With `--print=opt` (accepted, although `--help` lists only `query, op, quad, optquad, plan`), `q2` became `(project (?boss) (bgp (triple ppl:Ben rel:reportsTo ??P0) (triple ??P0 rel:reportsTo ?boss)))`, while `q3` was unchanged. The spec rewrites a sequence into triple patterns during translation, but Jena keeps `seq` as a path in its raw algebra and flattens it only in its optimizer. That changes *when* the rewrite happens, not the result. Once flattened, `q2` is exactly the basic graph pattern from `bgp-first-select.md`. On version B the BGP yields two distinct mappings with Bob as the end, one with `??P0` bound to Alice and one with `??P0` bound to Monica, plus a third with `??P0` bound to Monica and the end at Alice. Each has card 1, and, as `modifier-distinct.md` established, Project drops `??P0` without merging, so `{?boss → Bob}` ends up with card 2.

The `path+` operator has no hidden variable to project, because it is evaluated by §18.4's function ALP. For a term start, OneOrMorePath first takes one step, `Let X = eval(x, path)`, and then for each node in that set calls `ALP(n, path, V)` with a single shared V. ALP's body is `if ( x in V ) return`, `add x to V`, then a recursive call for every node one step further on. The result is V itself, so a node is either in it or not. That is why the Bob rows of `q1` and `q3` collapse to one, and why the cycle in version C ends instead of looping. ZeroOrMorePath calls `ALP(X, path)` on the start node itself, and `add x to V` runs before `eval` is ever consulted, so the start term is always in the result.

## Design rationale

A fixed-depth alternative, a UNION of one-, two- and three-step sequences, would differ from `q3` in two concrete ways. It would repeat Bob, who has several routes of length two and three from Ben, and it would silently miss anyone four or more arrows away. `+` has no fixed maximum length, yet on a finite graph it does at most one expansion per node, because each node enters V once. So `+`/`*` suit a connectivity question such as "everyone above Ben". Explicit `/` sequences are right when the length matters or the intermediate nodes should be visible, because `+` cannot say how far away a node is or which route reached it. With `/`, duplicates are part of the answer and are removed deliberately, if at all, with DISTINCT.

## Edge cases

`q6` is the edge case most likely to surprise. The zero-length part of `*` does not require the start node to occur anywhere in the graph, so any IRI written as the subject comes back as its own match. `q5` is the milder version, since James occurs in the graph with other predicates only. A cycle gives a start node a genuine path of positive length back to itself, so `+`, which excludes only length zero, returns Ben from Ben on version C. When both ends are variables, the spec ranges the zero-length case over `nodes(G)`, every subject and object term in the graph. That case was read in the spec but not run.

## Worked example

Take version C's six `rel:reportsTo` arrows: Bob→Ben, Alice→Bob, Ben→Alice, Ben→Monica, Monica→Bob and Monica→Alice. The query is `q3.rq`, `select ?boss where { ppl:Ben rel:reportsTo+ ?boss }`. OneOrMorePath first takes one step from Ben, giving the set {Alice, Monica}, and starts with V empty. It calls ALP on Alice, which is not in V, so Alice is added. Alice's one step reaches Bob, who is not in V, so Bob is added. Bob's one step reaches Ben, who is not in V either, because the start itself was never added for `+`, so Ben is added. Ben's step reaches Alice, already in V, so that call returns at once, and Monica, who is not, so Monica is added. Monica's steps reach Bob and Alice, both already in V, so both calls return immediately. Back at the top level, the second starting node Monica is already in V and returns. V is now {Alice, Bob, Ben, Monica}, which gives four solutions, each with card 1. Fuseki returned exactly those four, Alice, Bob, Ben and Monica. Ben→Alice→Bob, Ben→Monica→Bob and Ben→Monica→Alice→Bob are three routes to Bob, so a per-route count would have listed Bob three times.
