# BIND and VALUES: Introducing Bindings Inline (local-engine)

## Overview

This exercise introduces two ways of putting bindings into a query directly instead of matching them from triples. `BIND(expr AS ?v)` computes a new variable from each solution, and `VALUES` writes a small table of solutions into the query, which is then joined with the rest. The dataset `assign-bind-values/data.ttl` holds 9 triples about five people. Bob has age 30 and height `193.`, which Turtle reads as the integer 193 followed by the statement's closing dot. Alice has age 11 and the blank node `_:unknown` as her height. Ben has age `40.0` (`xsd:decimal`) and no height at all. Monica's age is the non-canonical `"030"^^xsd:integer` and her height is `"150"^^xsd:double`. James has age 16 and the plain string `"160 cm"` as his height. Seven queries, `q1.rq` to `q7.rq`, were each predicted before they ran. The target is `local-engine`. The primary engine was Apache Jena Fuseki 6.2.0, built from the official docker kit. A fresh lookup preferred it over Oxigraph because it keeps a stored lexical form such as `"030"` exactly as written, which the term-versus-value comparison in `q6` and `q7` depends on. A silent panel ran every query: Oxigraph 0.5.13, Eclipse RDF4J 6.1.0, QLever, Virtuoso Open Source 7.2.18-dev, Tentris 1.6.0 and MillenniumDB built from its repository at commit 126c387.

## BIND as Extend, and why position matters

The algebra turns `BIND` into Extend, already met in `agg-set-functions.md`. There it attached an aggregate's alias, and its second clause, which returns the solution unchanged when the expression is an error, explained an unbound aggregate. The full definition in §18.5 has three clauses. When the expression yields a value, that value is added under the new variable. When it is an error, the solution μ is returned as it was, so the row survives with the variable absent. When the variable is already in the solution's domain, Extend is undefined. No "error" value is ever bound, because a binding always pairs a variable with an RDF term. The errors themselves come from the rule recorded in `filter-unbound.md`: every operator except `BOUND`, `COALESCE`, `EXISTS` and `NOT EXISTS` raises a type error on an unbound argument, and arithmetic also raises one on a blank node or a string. The result datatype of arithmetic follows the promotion ladder from `agg-set-functions.md`, integer to decimal to float to double, with the integer-over-integer exception that division returns a decimal.

Position matters for BIND in a way it does not for FILTER. §18.2.2.6 translates a group by walking its elements in order and rebuilding one pattern G each time. A triple block becomes `G := Join(G, A)`, an `OPTIONAL` becomes `G := LeftJoin(G, A, true)` and a `BIND` becomes `G := Extend(G, var, expr)`. An Extend therefore sees only the variables bound by the elements before it. A FILTER, by contrast, is collected and applied to the whole group, as `filter-unbound.md` showed. §10.1 adds the matching syntax rule: the variable introduced by BIND "must not have been used in the group graph pattern up to the point of use in BIND."

## VALUES as a join on terms

`VALUES` supplies a multiset of solution mappings that "are combined with the results of query evaluation by a join operation" (§10.2). A cell holding `UNDEF` leaves that variable out of the row's mapping, so the row `(UNDEF UNDEF)` is the empty mapping `{}`. The join uses compatibility exactly as `optional-unbound.md` defined it: only variables in both domains are compared. §18.3 states what "equal" means there: "μ1(v) and μ2(v) are the same RDF term." `IN` is the opposite choice, because §17.4.1.9 tests membership "with "=" operator, which tests for the same value", and expands to an `||` chain of equalities.

## Observable behavior

On Fuseki, `q1` (required age and height, `BIND(?height / ?age AS ?progress)`) returned 4 rows. Bob's progress was `"6.433333333333333333333333"^^xsd:decimal` and Monica's was `"5.0e0"^^xsd:double`, while Alice and James were unbound. `q2` moved the height pattern into `OPTIONAL` and returned 5 rows, Ben's row having `?height` and `?progress` both unbound. `q3` added `FILTER(?height / ?age > 0)` and kept only Bob and Monica. `q4` was `q2` with the BIND moved before the OPTIONAL. It returned the same 5 rows with every height filled in and every `?progress` unbound. `q5`, which binds `AS ?age` after a pattern using `?age`, returned HTTP 400 with "BIND: Variable used when already in-scope". `q6` put `VALUES (?age ?height) { (30 UNDEF) (UNDEF 150) (99 193) }` before the two required patterns and returned Bob alone. `q7` replaced the block with `FILTER(?age IN (30) || ?height IN (150))` and returned Bob and Monica.

## Internal mechanism

Fuseki's algebra printer was not run this session. The algebra below was derived by hand from the §18.2.2.6 loop. For `q2` the loop builds an Extend over a LeftJoin of the age pattern and the height pattern, so the division sees each person's height when there is one. For `q4` it builds a LeftJoin over an Extend of the age pattern alone. At that Extend, Bob's row is only `{ ?person → ppl:Bob, ?age → 30 }`, so `?height / ?age` raises an error, Extend's second clause returns the row unchanged, and `?progress` is never added. The LeftJoin then brings in heights, but nothing re-evaluates an Extend that has already run. In `q6` the join pairs each VALUES mapping with each of the four BGP solutions. `{ ?age → 30 }` is compatible with Bob only, because Monica's `"030"^^xsd:integer` is a different term from `"30"^^xsd:integer`. `{ ?height → 150 }` matches nobody, because the integer `"150"` is not the double `"150"`.

## Design rationale

BIND and FILTER give the same expression opposite effects on rows. As a BIND, the division kept all five people of `q2` and showed where it failed. As a FILTER in `q3`, the error quietly removed three of them. A query that must report failed computations should compute with BIND and decide with FILTER, as `q3` did. BIND also has to be placed after every pattern its expression reads, and `q4` confirms that a misplaced BIND fails silently instead of being rejected. Between VALUES and `IN`, the trade is term against value. VALUES is a join, so it can add duplicate rows: in the sign-off variation, adding `(UNDEF UNDEF)` to `q6` gives 5 rows with Bob twice, by reasoning rather than a run. It also depends on the exact stored spelling. `IN` filters each solution once and compares values, so `q7` returned the same two rows on all seven engines, while `q6` split three ways. Deliberately duplicating rows with VALUES so they can be grouped differently later, much like SQL's GROUPING SETS, is the case where the join behavior is wanted.

## Edge cases

The panel separated evaluation bugs from storage choices. Oxigraph, QLever, Virtuoso, Tentris and MillenniumDB stored `"030"` as `"30"` when loading the data, so on them `q6` also matched Monica. QLever stored integers as `xsd:int` and Monica's double as a decimal. MillenniumDB stored Bob's `193.` as the plain string `"193"`, so his division errored on that engine only. In `q4` it bound Ben's progress to `3.75E0`, which is 150 divided by 40, a value crossing between rows. Virtuoso divided integers to integers (Bob `"6"`), gave James `"0"` instead of an error, answered `q5` with HTTP 200 and no rows, and joined integer 150 to double 150 in `q6`, returning Monica twice.

## Worked example

Take `q6` over the dataset. The two required patterns match Bob, Alice, Monica and James, each with age and height, and Ben drops out for lacking a height. The VALUES block becomes three mappings: `{ ?age → "30"^^xsd:integer }`, `{ ?height → "150"^^xsd:integer }` and `{ ?age → 99, ?height → 193 }`. For the first, the only shared variable is `?age`. Bob's `"30"^^xsd:integer` is the same term, so the merge is Bob's whole solution. Monica's `"030"^^xsd:integer` has the same value but a different lexical form, so it is incompatible. For the second, Monica's height is `"150"^^xsd:double`, with the same spelling but a different datatype, so it is again a different term, and nobody else has 150. The third needs age 99, which nobody has. The join therefore yields exactly one row, Bob with `"30"^^xsd:integer` and `"193"^^xsd:integer`, which is what Fuseki and RDF4J returned. Rewriting the filter as `?age IN (30)` compares by value instead, and Monica's `"030"` equals 30, so `q7` keeps her.
