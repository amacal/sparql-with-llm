## Steps

1. **Full prerequisite chain.** List every concept the topic depends on, as deep as the chain goes (a dependency's own dependencies count too).

2. **Check coverage of each prerequisite.** Derive `<slug>` from the exact title via `.index/schema.yml`'s `slug_algorithm` and `Read .index/sessions/<slug>/meta.yml` first — confirms coverage fast, gives the exact file/target/date/status, plus `prerequisites.yml`/`derived_from.yml`/`uses_concepts.yml` for the genuine dependency shape (if the slug guess is wrong, `grep -l 'title: "<title>"' .index/sessions/*/meta.yml` finds the right directory). Note the `status` field specifically: if it's still `demonstrated` (not yet `retained`), say so explicitly in your report rather than treating it as fully settled — still usable as a prerequisite early on (see CLAUDE.md's "Fast index"), but worth flagging as a candidate for its own retention check if one isn't already scheduled (`ls .index/cold-runs/` to check). Then `Read` that prerequisite's notes file for the specific algebra/mechanism fact the new session should reuse rather than re-derive (per "Notes writing style"), and for any caveat that file leaves explicitly unresolved ("not investigated", "untested", "only observed once") about a pattern the new exercise will reuse — an open caveat carried forward silently can surface mid-session as an unplanned failure. `grep -l '"<title>"' .history/*/*.yml` to find its history entry, `Read` that one file for session-event context (a known bug already hit, a wrong prediction already corrected, work already deferred) — and if that entry's `corrections` holds a corrected misconception about a definition the new topic directly reuses (not a passing detail), carry it into report item (b) as a one-question recap check to run before the new material, since a fact corrected once and then reused unchecked tends to need correcting again mid-session. `.history/` carries no algebra/mechanism content and no dependency field. Don't grep every history file's full content when you only need the one entry.

3. **Flag genuinely new material.** What within the topic isn't covered by any existing prerequisite — this needs full Socratic derivation from first principles, anchored with a concrete tiny dataset and expected-result example before any formal question (per "Pacing and assumed knowledge").

4. **Flag missing prerequisites.** `ls .index/future-targets/` (each filename's `title:` field is a topic explicitly named as future work but not yet done) — exactly this case. Cross-check `.history/` if `.index/` looks stale. Say so explicitly — may mean a review is owed first (per "Theory review"), or the topic isn't actually ready yet.

5. **Decide the target environment.** `local-engine` is the default whenever the topic needs a running SPARQL endpoint. `formats` instead when the topic is genuinely about RDF serialization or SPARQL result-format mechanics with no query evaluation involved. `remote-endpoint` instead when the topic genuinely needs real network/scale/federation behavior a small local container can't honestly teach — name specifically what that is. A managed/cloud-hosted target only when the topic genuinely needs a real platform-specific capability — name exactly which credential is needed; the calling conversation asks the user for it rather than silently deferring the topic. Note if the topic re-covers a pattern already implemented against a different engine/format already covered — if so, say that part should be a quick review/citation, not fresh derivation, and that the exact Concept Title needs the target-disambiguation suffix per `.index/schema.yml`'s `cross_target_disambiguation`.

6. **For a `local-engine` topic, decide the concrete engine — live, not from memory.** Per CLAUDE.md's "No hardcoded technology": actually look it up (WebFetch/WebSearch) for what's currently mainstream, actively maintained, and freely available, biased toward one that's a good fit for *this specific topic* (e.g. one with solid property-path support if that's the topic, one offering a visible query plan if "Internal mechanism" needs it). State the concrete choice and a one-line reason. Then, the same live way, pick the silent panel of further engines every query will also run against (see CLAUDE.md's "Cross-engine and cross-format comparison") — as many as are practical to stand up, each currently mainstream and freely available, never the previous exercise's panel carried over by habit — naming each with a one-line reason and its load mechanism, and confirming each actually has a usable image or official build kit right now. For a `formats` topic, decide the concrete format(s) the same deliberate way, biased toward whichever format pairing makes the preserved-versus-lost comparison most informative for this specific topic.

7. **Suggest a short directory name** for the exercise (`{target-dir}/{dir}/`, a short human-friendly name, not the full slug) following the grouping convention (shared prefix with related existing exercises under that target). The main conversation creates the empty directory; the user writes every file in it (fresh, or carried over from their own earlier exercises per CLAUDE.md's "Exercise files"). That includes any deliberately invalid input a step needs (a malformed line to provoke a parse error, a negative test case) — it is dataset content like any other, so plan it as a user-written file in the exercise directory, never as a Claude-written fixture under `.tmp/`; only the verification commands and helper scripts that run it are Claude's.

8. **Cross-repo transfer decision.** If `.skills/session-select.md`'s step 1c already flagged a genuine overlap for this topic, decide which of the three outcomes in CLAUDE.md's "Cross-repo transfer" actually fits — cite, bridge, or independent — and say which, with the specific reason (the sibling's evidence status, and whether this repo's own domain/hard constraints genuinely let you skip or shorten the from-scratch work). Never leave it undecided for the calling conversation to guess at; "independent, from scratch" is itself a valid, explicit decision, not a default to fall into silently.

9. **Report back** a structured plan: (a) prerequisites to cite-and-confirm briefly, each with source notes file, its `status` (`demonstrated`/`retained`), and the specific fact to reuse, plus any unresolved caveat that file records about a reused pattern, so the calling conversation can decide whether to raise it deliberately or leave it as a prediction test; (b) any prerequisite needing a deeper review first, and why, plus any one-question recap check carried over from a prerequisite's `corrections` in step 2; (c) what's genuinely new, plus a suggested concrete dataset/pattern anchor for opening it, and for each spec section the dialogue will quote, its section number and its `id="..."` anchor in the raw page (never a character offset — the calling conversation cuts excerpts from the raw page by anchor, per CLAUDE.md's "Teaching style"); (d) the decided target environment and why; (e) the decided concrete primary engine and silent panel, or format(s), with the one-line reasons from step 6; (f) a suggested exercise directory name; (g) the cross-repo transfer decision from step 8, if applicable. No Socratic question script — the calling conversation designs the actual dialogue from this plan.
