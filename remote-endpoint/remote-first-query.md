# First Query Against a Remote Public SPARQL Endpoint (remote-endpoint)

## Overview

Every earlier exercise checked a query against a hand-written dataset, so the expected result could be read straight off a `.ttl` file. This exercise queries a real, shared, public endpoint holding hundreds of millions of triples nobody here wrote, and asks how a hand-derived expected result is still possible. The answer the session reached is a two-step method. First, run a narrow, bounded inspection query and prove that its result is *complete*, so the slice it returns can stand in for the dataset file. Second, predict a different query's result purely from that slice, then run it and compare. The user-written queries `q1.rq` to `q8.rq` trace the path from an arbitrary sample to a complete, checkable slice.

The endpoint was DBpedia, `https://dbpedia.org/sparql`, which answered as `Virtuoso/08.03.3334` and `Virtuoso/08.03.3335` (two builds behind the same URL). A fresh live lookup at planning time chose it because it is mainstream, free, needs no credentials, and has a flat data model (resource IRIs, `rdfs:label` names, `owl:sameAs` links). Its own documentation also describes silent result truncation, which bears directly on an open question from `modifier-order-slice.md`. The runner-up was the Wikidata Query Service. Every result below was observed on 2026-10-14 and is a snapshot: DBpedia's data changes between releases, so the exact counts may drift later.

## Proving a slice complete on this endpoint

`modifier-order-slice.md` established that `LIMIT` without `ORDER BY` cuts a sequence whose order was never fixed, so it returns an arbitrary subset. A slice is useful as evidence only if it contains *every* triple matching its pattern. Getting back fewer rows than the `LIMIT` is the first test: the pattern ran out of matches before the limit cut anything. On DBpedia that test is not enough on its own. The endpoint's own page states `ResultSetMaxRows = 10000` and `MaxQueryExecutionTime = 120` seconds, and warns that "Partial result sets are returned the same way as complete result sets. There is no HTTP error status code; just a 200 OK code)". It adds that a row-capped result carries an `X-SPARQL-MaxRows` response header, and a timed-out one carries `X-SQL-State`, `X-SQL-Message`, `X-Exec-Milliseconds` and `X-Exec-DB-Activity`. So proving completeness here needs three facts together: fewer rows than the `LIMIT`, no `X-SPARQL-MaxRows` header, and no timeout headers. The two header checks are a DBpedia/Virtuoso convention, not part of the SPARQL standard. They also answer the question left open in `modifier-order-slice.md`: on this endpoint Virtuoso is documented to signal a capped result, but only through a header, never through the status code.

## Observable behavior

`q1.rq` (`?subject ?predicate ?object`, `limit 10`) returned exactly 10 rows with all three variables bound, as predicted. All 10 subjects, though, were Virtuoso's internal metadata (`virtrdf#DefaultQuadMap` and similar), not facts about the world. `q2.rq` fixed only the object, to `"Tentris"@en`. It failed twice with HTTP 500 and `Virtuoso 22023 Error SR549: Both datatype id 310 and language id 295 are not default in call of rdf_box()`. `q3.rq` fixed the predicate to `rdfs:label` as well. It returned HTTP 200 with zero bindings, where one row had been predicted. `q4.rq`, the same shape with `"Munich"@en`, returned two subjects, `dbr:Munich` and `dbr:Category:Munich`, against a prediction of one. `q5.rq` (Munich as subject, `limit 100`) returned exactly 100 rows: 89 `owl:sameAs`, 7 `rdf:type`, 4 `rdfs:seeAlso`, and no `rdfs:label`. The prediction had been fewer than 100. `q6.rq` (subject and predicate fixed) returned exactly 100 at `limit 100`, again against a prediction of fewer. At `limit 1000` it returned 149 rows with no `X-` headers, so the slice was complete. `q7.rq`, with every position fixed and the object set to the absent IRI `wikidata:Q1726X`, returned `"bindings": [ ]` as predicted, under `"vars": ["_star_fake"]`. `q8.rq`, with the present IRI `wikidata:Q1726`, returned one solution as predicted, but that solution bound `_star_fake` to `"1"^^xsd:integer`.

## Internal mechanism

Each query is a single triple pattern, so its algebra is one basic graph pattern followed by projection and a slice, as in `bgp-first-select.md`. The pattern yields one solution mapping per matching triple, binding only its variables. For `q6.rq` that means 149 mappings `?object → X`, one for each triple `<Munich> owl:sameAs X`. They come out in the engine's own order, and `limit 1000` let all of them through. A subject–predicate index lookup is plausible but unverified, since no plan was fetched. `q1.rq` showed that the default dataset this endpoint queries includes the engine's own bookkeeping triples alongside DBpedia's. Which collection a query matches against is a named-graph question, not yet taught. The empty `q3.rq` and the two-row `q4.rq` both follow from term equality. As `rdf-literal-datatypes.md` established, `"Tentris"` (`xsd:string`) and `"Tentris"@en` (`rdf:langString`, tag `en`) are different terms, and SPARQL applies no fallback tag. A pattern matches only identical terms, and nothing makes a label unique: two IRIs carrying the same label give two solutions. When a pattern has no variables at all, a match produces one solution that binds nothing. §5.2.1 says the empty group pattern matches "with one solution that does not bind any variables", and §16.1.1 defines `SELECT *` as "all of the variables that appear anywhere in the query", which here is none. The standard result for `q8.rq` is therefore `"vars": []` and `"bindings": [ {} ]`. This is derived from the spec, not observed; Virtuoso's invented `_star_fake` variable is its own artifact.

## Design rationale

The queries narrow one fixed position at a time, because a prediction can only be checked against a set of triples you can read in full. `q1.rq` with a large limit would hit the 10,000-row cap, load a shared server for nothing, and return an arbitrary sample whose completeness could never be proved. Fixing the subject gave a coherent topic. Fixing the predicate too made the slice small enough to finish under the limit. Fixing all three turned a question about the slice into a yes/no lookup whose answer could be read off the saved list before running anything. Raising `q6.rq`'s limit from 100 to 1000 was polite because the subject and predicate were both fixed: the engine only reads Munich's `sameAs` triples. The same increase on `q1.rq` would not have been. Prefixes were declared with SPARQL `PREFIX`, though DBpedia pre-declares many, so the queries stay portable. For the empty result, a control query with the same shape on a name certain to exist (`q4.rq`) separated "the shape doesn't work" from "this name isn't there".

## Edge cases

An empty result on data you didn't write is ambiguous. Zero rows for `q3.rq` is consistent with four explanations: DBpedia has no such resource, it states the name with a different predicate, it spells the name differently, or it uses a different tag or none. The Munich control rules out only a broken query shape. It makes the predicate and tag explanations less likely but cannot settle any of the four for Tentris, so it stays unresolved. `q2.rq`'s HTTP 500 is an engine failure on legal SPARQL; §2.1.7 of the Protocol reserves 400 for a query that isn't legal by the grammar. Exactly hitting the `LIMIT` is likewise ambiguous on its own. In `q5.rq` the missing label triple, already known from `q4.rq` to exist, proved that more than 100 triples were there.

## Worked example

Take the two triples `q4.rq` revealed: `<http://dbpedia.org/resource/Munich> rdfs:label "Munich"@en` and `<http://dbpedia.org/resource/Category:Munich> rdfs:label "Munich"@en`. The pattern `?subject rdfs:label "Munich"@en` compares each triple's predicate and object with the fixed terms. Both triples have the identical predicate and the identical literal: lexical form `Munich`, datatype `rdf:langString`, tag `en`. So both match, and the result is two solutions binding `?subject` to the two IRIs. DBpedia returned exactly that; the prediction of one assumed labels are unique. A triple `<X> rdfs:label "Munich"` without the tag would not have matched, because its datatype is `xsd:string`.

Now take the slice from `q6.rq`: 149 objects of `<Munich> owl:sameAs ?object`, proved complete by 149 being under `limit 1000` and by the absence of any `X-` header. Searching that saved list for `http://www.wikidata.org/entity/Q1726X` finds no line. So the fully fixed pattern in `q7.rq` can match no triple, and the result has no solutions: `"bindings": [ ]`, which is what came back. Searching for `http://www.wikidata.org/entity/Q1726` finds exactly one line, so `q8.rq`'s pattern matches exactly one triple. With no variables to record, that match is one empty solution, which the standard writes as `[ {} ]`. DBpedia returned one solution too, matching the predicted count. Its content, `_star_fake` bound to `1`, is where this engine departs from the spec.
