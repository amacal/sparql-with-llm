# Language-Tagged Labels with lang() and langMatches() (remote-endpoint)

## Overview

This exercise selects a resource's names by language on a real public endpoint, DBpedia (`https://dbpedia.org/sparql`, answered by Virtuoso 08.03.3334 and 08.03.3335 behind the same URL). DBpedia was chosen at planning time for continuity with the earlier remote session recorded in `remote-endpoint/remote-first-query.md`: it is free, credential-free, its documented result cap and truncation headers were already known, and Munich already had a complete, inspected slice there. Intuitively, a single resource such as Munich carries many `rdfs:label` triples, one name per language, and the question is how a query keeps only the names in one language. SPARQL offers two tools for that. The first is an exact comparison on the tag extracted by `LANG`, and the second is the range-matching function `langMatches`. A second strand of the session then used `LANG` on a term that is not a literal at all, to watch a type error travel through `||` and `&&` inside a `FILTER`.

## How a language tag is read and matched

The RDF side is reused from `formats/rdf-literal-datatypes.md`: a language-tagged literal is a lexical form plus a tag, its datatype is `rdf:langString`, and a parser may lowercase the tag. SPARQL 1.1 Query §17.4.2.6 defines `LANG (literal ltrl)` as returning a simple literal holding the tag, or `""` when the literal has no tag. So `lang("München"@de)` is the plain string `"de"`, and comparing it with `= "DE"` is an ordinary string comparison between two different strings, which is false. The function `langMatches(tag, range)` (§17.4.3.13) instead returns an `xsd:boolean` under RFC 4647 §3.3.1 basic filtering. It is true when, ignoring case, the range equals the whole tag, or equals a leading part of the tag that is immediately followed by `-`. The first argument is the tag from the data (in practice `lang(?x)`) and the second is the range the query author types. Only shortening the range widens the match: `"de"` covers `de`, `de-AT` and `de-CH`, but never `den`, and a range can never match a middle or trailing subtag such as `AT`.

The functions `LANG` and `isIRI` also behave differently on an IRI. `LANG` declares a literal parameter, and §17.3 says a function invoked with an argument of the wrong type produces a type error. `isIRI (RDF term term)` (§17.4.2.1) accepts any term and simply answers true or false. How `FILTER` and the logical operators treat that error is the three-valued logic already recorded in `local-engine/filter-unbound.md`. Here the error comes from a wrong argument type rather than from an unbound variable, but it follows the same §17.2 rules.

## Observable behavior

`q1` (`res:Munich rdfs:label ?label`, `LIMIT 1000`) returned 29 labels with no `X-` headers, so the slice is complete. Every label was language-tagged, across 22 distinct tags, all bare primary codes with no subtags. Seven tags appeared twice, among them `de`, because the endpoint also lists labels such as "U-Bahnhof Thalkirchen" under Munich. `q2` with `filter(lang(?label) = "de")` returned 2 rows, `"U-Bahnhof Thalkirchen"@de` and `"München"@de`. `q3` with `= "DE"` returned no rows, and `q4` with `langMatches(lang(?label), "DE")` returned the same 2 rows as `q2`. The pattern `res:Munich <http://dbpedia.org/property/source> ?o` has exactly 2 objects (confirmed by an unfiltered cross-check), the IRI `dbr:World_Meteorological_Organization` and `"DWD SKlima.de Infoclimat"@en`. `q5` with `filter(isIRI(?o) || lang(?o) = "en")` returned both, and `q6` with `&&` returned none. Every count matched the prediction stated before the run.

## Internal mechanism

Each query first matches its single triple pattern, producing one solution per object, and then the group's `FILTER` evaluates its expression once per solution, keeping only those where the result is true. A filter's position inside the group does not matter: `q2`–`q4` write the `filter` before the triple pattern, and it still constrains the whole group. In `q3` every solution yields `lang(?label)` as a lowercase string such as `"de"`, and `"de" = "DE"` is false for all 29 rows. In `q4`, `langMatches("de", "DE")` is true because the comparison ignores case, while every other tag fails to equal `"de"` and has no `-` to qualify as a prefix. In `q5` and `q6` the IRI row evaluates as `T` on the left side and `E` on the right, and the literal row as `F` on the left and `T` on the right. Under §17.2, `T || E` is `T` and `F || T` is `T`, so `q5` keeps both rows, while `T && E` is `E` and `F && T` is `F`, so `q6` keeps neither. For the IRI row, the row is dropped because of an error, not a false result.

## Design rationale

Using `langMatches(lang(?label), "de")` asks for German in any regional variant, which is usually what a reader wants from a label. An exact `lang(?label) = "de-AT"` is the deliberate choice when one specific regional variant is required and the others must be excluded. The exact form also depends on how a parser normalised the tag's case, which `langMatches` sidesteps. The `isIRI(?o) || ...` shape shows why the ordering of concerns matters on real data. A property such as `dbp:source` mixes IRIs and literals in its objects, so any expression that assumes a literal will error on some rows, and wrapping it in an `||` with a type test keeps those rows deliberately, rather than losing them silently. This session reused the earlier Munich data instead of a fresh resource, so that the 29-label slice could be proved complete before anything was filtered.

## Edge cases

None of Munich's 29 tags has a subtag, so `q4` exercised only the case-insensitive equality clause of RFC 4647, and the `-` prefix clause was reasoned through in dialogue rather than observed. A label with no tag would give `lang(?label) = ""` and would be false under `= "de"`, and `langMatches("", "*")` is false because `"*"` matches only non-empty tags. No such label existed here. `q5` and `q6` carry no `LIMIT`. Both fix the subject and predicate and were shown to have 2 objects, but this differs from the bounded-query etiquette the earlier remote session kept.

## Worked example

Take the two `dbp:source` triples of Munich: `dbr:Munich dbp:source dbr:World_Meteorological_Organization` and `dbr:Munich dbp:source "DWD SKlima.de Infoclimat"@en`. Matching `res:Munich <http://dbpedia.org/property/source> ?o` yields two solutions, one binding `?o` to the IRI and one binding it to the English literal. In `q5` the filter is `isIRI(?o) || lang(?o) = "en"`. For the first solution `isIRI` is true, and `lang` receives an IRI where a literal is required, so it raises a type error, which makes the comparison an error too. A logical-or with one true branch is true regardless of an error on the other, so the solution is kept. For the second solution `isIRI` is false, `lang` returns `"en"`, and the comparison is true, so `F || T` is true and this solution is kept as well. The observed result was exactly these two rows.

Change only `||` to `&&` and evaluate the same two solutions. For the IRI, `T && E` is an error, because a logical-and with an error on one branch returns the error when the other branch is true. For the literal, `F && T` is plain false, with no error anywhere. `FILTER` keeps only true, so both solutions are removed, and the endpoint returned `"bindings": []` with HTTP 200. The labels give a second, shorter trace. Of Munich's 29 labels exactly two carry the tag `de`. `lang(?label) = "DE"` compares `"de"` with `"DE"`, which is false for both, giving 0 rows, while `langMatches(lang(?label), "DE")` compares them ignoring case and gives the same 2 rows as `= "de"`.
